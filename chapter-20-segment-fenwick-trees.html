CHAPTER TWENTY · GAP-FILLING SET

Segment Trees & Fenwick Trees

Chapter 2.4's prefix sums had one silent limitation, flagged back then but never solved: they fall apart the moment the underlying array actually changes. This chapter is the fix — and it turns out to be Chapter 12's heap-style "precompute, don't recompute" idea, applied to ranges instead of a single min/max.

20.1The gap prefix sums couldn't fill

Fast range queries AND fast updates — a combination nothing else in this book offers

+

Recall Chapter 2.4's honest trade-off: prefix sums give O(1) range-sum queries after an O(n) one-time build — but if a single element changes, every prefix sum after it is now wrong, forcing a full O(n) rebuild. If updates happen frequently, interleaved with queries, prefix sums stop being a good deal at all.

💡 THE GENUINE GAP

What's actually needed: a structure offering both fast range queries and fast point updates — not one at the expense of the other. Arrays give O(1) point updates but O(n) range queries. Prefix sums give O(1) range queries but O(n) updates. Neither wins both. Segment trees and Fenwick trees are two different, genuinely clever answers to exactly this — both land on O(log n) for both operations, a real, honest middle ground rather than a trick that secretly favors one side.

20.2Segment trees — a tree of pre-merged answers

Chapter 10's recursive template, applied to ranges instead of subtrees

+
🏢 THE COMMITTEE-OF-COMMITTEES ANALOGY

Picture a company where the CEO's "total headcount" figure isn't recomputed from scratch by personally counting every employee — instead, each department manager reports their own department's total, and the CEO just adds up the department totals. Each department manager, in turn, gets sub-team totals reported up to them, rather than counting individually themselves. A segment tree is exactly this org chart, applied to array ranges: the root represents the sum (or min, max, or any other "mergeable" property) of the entire array, each child represents half that range, and so on recursively down to individual elements as the leaves.

Array: [2, 5, 1, 4, 9, 3] sum[0..5]=24 / \ sum[0..2]=8 sum[3..5]=16 / \ / \ sum[0,1]=7 [2]=1 sum[3,4]=13 [5]=3 / \ / \ [0]=2 [1]=5 [3]=4 [4]=9

Answering a range query means walking down from the root, and the moment a node's range falls entirely inside the queried range, you use its precomputed value directly and stop descending further into it — exactly the CEO trusting a department manager's total rather than personally re-verifying every employee underneath them.

🧠 WHY QUERIES ARE O(log n) — THE SAME HEIGHT ARGUMENT AS CHAPTER 12

Any query range decomposes into at most O(log n) of these "fully covered" nodes — because at each level of the tree, a query range can only partially overlap at most 2 nodes (one at each edge of the range) before fully covering everything in between, and there are only log n levels total (this is Chapter 12.3's "complete tree has guaranteed log n height" argument, reused here). So a query touches at most O(log n) fully-covered nodes plus a small, bounded number of partial ones per level — genuinely O(log n) total, not O(n).

20.3Updates — fixing only what changed

Why changing one leaf doesn't mean rebuilding the whole tree

+

Updating a single array element means walking from that element's leaf back up to the root, recomputing each ancestor's merged value along the way — since only the ancestors of the changed leaf could possibly be affected, everything else in the tree is provably untouched.

def update(node, node_lo, node_hi, idx, new_val):
    if node_lo == node_hi:
        tree[node] = new_val
        return
    mid = (node_lo + node_hi) // 2
    if idx <= mid: update(2*node, node_lo, mid, idx, new_val)
    else: update(2*node+1, mid+1, node_hi, idx, new_val)
    tree[node] = tree[2*node] + tree[2*node+1]   # re-merge from children, one level up
🧠 WHY THIS IS O(log n), NOT O(n) — THE SAME "ONLY THE PATH MATTERS" IDEA AS CHAPTER 11

A single leaf has exactly one path back to the root, and that path's length is the tree's height — O(log n) for a balanced segment tree, by construction (segment trees are always built as complete, balanced binary trees on top of the array, regardless of the array's own values — unlike Chapter 11's BST, there's no adversarial-input risk here at all, since the tree's shape depends only on the array's length, never its contents). Every node off that single path is completely unaffected and never touched, which is exactly why the update is genuinely logarithmic, not linear.

This query-and-update pairing — both O(log n) — is the entire point: segment trees generalize far beyond sums to any "mergeable" operation (min, max, GCD, even more exotic custom combinations), as long as merging two children's answers can produce the correct parent answer, echoing Chapter 15.3's "define the state, then the combine rule" DP discipline, just applied to a static array structure instead of a table.

20.4Fenwick trees — the lean alternative

Chapter 17's bit tricks, arriving to solve one more problem

+

A Fenwick tree (Binary Indexed Tree) solves the exact same prefix-sum-with-updates problem as a segment tree, but specifically for sums (not general min/max), using dramatically less code and memory — by directly reusing Chapter 17.3's n & (-n) lowest-set-bit trick.

📇 THE "EACH INDEX OWNS A SPECIFIC RANGE, DETERMINED BY ITS OWN BITS" IDEA

Each index i in a Fenwick tree is responsible for summarizing a specific range of the original array — and remarkably, the size of that range is exactly determined by i's lowest set bit (Chapter 17.3's isolation trick). Index 12 (binary 1100, lowest set bit worth 4) is responsible for a range of 4 elements; index 8 (1000, lowest set bit worth 8) is responsible for 8. To compute a prefix sum up to index i, repeatedly jump backward by clearing the lowest set bit (i -= i & (-i), Chapter 17.2's domino trick) — each jump lands you on another index whose pre-summarized range you can add in directly, and because each jump strictly shrinks the number of "on" bits remaining, you're guaranteed to reach 0 in at most log n jumps.

tree = [0] * (n + 1)
def update(i, delta):
    while i <= n:
        tree[i] += delta
        i += i & (-i)         # move to the next index this one contributes to

def prefix_sum(i):
    total = 0
    while i > 0:
        total += tree[i]
        i -= i & (-i)          # jump back using the lowest-set-bit trick
    return total

✅ WHEN TO REACH FOR WHICH

If the operation is a plain sum (or any operation with a clean inverse, like XOR), Fenwick's leanness usually wins. If you need min/max, or any operation without a clean "undo," a segment tree is the honest choice — Fenwick's whole trick relies on being able to combine contributions additively, which min/max fundamentally can't do the same way.

20.5Where smart people trip up

+
⚠️ Trying to build a Fenwick tree for min/max

Fenwick's update/query logic depends on additive contributions that can be cleanly combined and, implicitly, "removed" — min and max have no such inverse operation, so a naive Fenwick-for-min implementation silently gives wrong answers on certain update patterns. Use a segment tree for min/max instead.

⚠️ Off-by-one errors from mixing 0-indexed and 1-indexed conventions

Fenwick trees are conventionally built 1-indexed specifically because the i & (-i) trick breaks down at index 0 (which has no set bits at all). Mixing a 0-indexed input array with a 1-indexed Fenwick tree without a consistent, deliberate offset is one of the most common sources of subtle bugs in this entire structure.

⚠️ Forgetting that segment tree array size needs roughly 4n, not 2n

Because a segment tree built on an array whose length isn't a clean power of 2 isn't perfectly balanced at the leaf level, the array-based representation needs extra headroom — allocating only 2n can silently cause index-out-of-range errors on certain array sizes that happen not to trigger it on others.

20.6Check your understanding

+
Q1 — Why does updating a single segment-tree leaf only require touching O(log n) nodes, not the whole tree?›

Only a node's ancestors depend on its value — every other node in the tree represents a completely different range that never included this leaf, so nothing about it changes. A single leaf has exactly one path to the root, and that path's length is bounded by the tree's height, which is O(log n) since the tree is always built as a complete, balanced structure regardless of the array's actual contents.

Q2 — In a Fenwick tree, why does repeatedly clearing the lowest set bit during a prefix-sum query guarantee termination in O(log n) steps?›

Each application of i -= i & (-i) removes exactly one "on" switch from i's binary representation (Chapter 17.2's domino trick) — since i can have at most log n switches total, this process must reach zero within at most log n steps, with no possibility of looping longer than that.

Q3 — Why can't a Fenwick tree be naively adapted for range-minimum queries the same way it handles sums?›

Fenwick's update mechanism relies on being able to combine and effectively "undo" contributions additively — sum has a clean inverse (subtraction), letting old contributions be cleanly replaced. Min has no such inverse: once you've combined several values into "the minimum so far," you can't recover what the second-smallest was to correctly update after the actual minimum changes, which is exactly why min/max needs a genuine segment tree instead.

This chapter is really two earlier ideas meeting for the first time: Chapter 10's recursive tree template, and Chapter 17's bit tricks — both solving the same "fast query, fast update" problem from two genuinely different angles.
