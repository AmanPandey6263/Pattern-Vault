Chapter 14 gave you the graph fundamentals. This chapter fills the specific holes that show up constantly in real interview loops and contests: finding the "weak points" of a network, finding tightly-knit clusters, and matching things up optimally.

19.1Bridges & Articulation Points

Finding the single points of failure in a network

+

An articulation point is a node whose removal splits the graph into multiple disconnected pieces. A bridge is the same idea for an edge instead of a node. Think of a road network: an articulation point is a town that, if it burned down, would cut off two regions from each other entirely; a bridge is a single road that, if closed, does the same thing.

🪢 THE "HOW FAR BACK CAN A ROPE REACH" ANALOGY

Run a DFS and assign every node a disc[] time — the order you first discovered it. Now track a second value, low[] — the earliest discovery time reachable from this node's subtree, including via one "back edge" that loops up to an ancestor. Picture every back edge as a rope thrown from deep in the tree back up to some ancestor. A node u's low[u] tells you: standing at u, how far up the tree can a rope from anywhere in my subtree reach? If none of u's children can throw a rope past u itself (i.e., low[child] >= disc[u]), then removing u genuinely severs that child's whole subtree from the rest of the graph — u is an articulation point. The bridge condition is nearly identical but strictly greater (low[child] > disc[u]): if the child's subtree can't even throw a rope back to u itself, the single edge connecting them is the only link — a bridge.

disc = {}; low = {}; timer = [0]
def dfs(u, parent):
    disc[u] = low[u] = timer[0]; timer[0] += 1
    for v in graph[u]:
        if v == parent: continue
        if v not in disc:
            dfs(v, u)
            low[u] = min(low[u], low[v])
            if low[v] > disc[u]:
                record_bridge(u, v)
            if low[v] >= disc[u] and parent is not None:
                record_articulation_point(u)
        else:
            low[u] = min(low[u], disc[v])   # back edge — a rope thrown upward
🧠 WHY THE ROOT NEEDS SPECIAL-CASE HANDLING

The root of the DFS tree has no parent to be cut off from — it's only an articulation point if it has two or more separate children in the DFS tree (each child subtree with no rope back to another child means the root is the only thing connecting those subtrees together). This is a genuine edge case worth testing explicitly, exactly the kind of boundary condition Chapter 11's BST-range logic trained you to hunt for.

19.2Strongly Connected Components

Finding clusters where everyone can reach everyone

+

In a directed graph, a Strongly Connected Component (SCC) is a maximal group of nodes where every node can reach every other node via directed edges, both ways. Think of a group chat where everyone can message everyone — versus a broadcast channel where only the admin can post, which isn't strongly connected at all.

🔄 KOSARAJU'S TWO-PASS TRICK

Here's a genuinely elegant idea: run a DFS on the graph and record nodes by finish time (Chapter 10's postorder — a node is "finished" once everything reachable from it has been fully explored). Then reverse every edge in the graph, and process nodes in decreasing finish-time order, running DFS again — each new DFS tree in this second pass is exactly one SCC. Why does reversing the edges and processing by finish time work? A node that finishes last in the first pass is, informally, "upstream" of everything else — it can reach the most. Reversing the graph and starting from it means you can now only explore what could originally reach it — intersecting "what I can reach" (from pass one) with "what can reach me" (from pass two, on the reversed graph) is precisely the definition of mutual reachability, which is exactly what an SCC is.

Tarjan's algorithm does this in a single DFS pass instead of two, using the exact same low[]/disc[] machinery from Section 19.1 plus an explicit stack tracking "currently on my active path" (echoing Chapter 14.4's directed-cycle two-set distinction) — when a node's low[] equals its own disc[], everything above it on the stack down to that point is one complete SCC, popped off together.

✅ WHY THIS MATTERS PRACTICALLY

Collapsing each SCC into a single "super-node" turns any directed graph into a DAG — which means Chapter 14.5's topological sort becomes available again, even on a graph that originally had cycles. This "condense then topologically sort" move is a genuinely common building block in harder graph problems.

19.3Bipartite Graphs & Matching

Splitting into two teams, and pairing things up optimally

+

A graph is bipartite if its nodes can be split into two groups such that every edge connects a node in one group to a node in the other — never within the same group. Think of job applicants and job postings: edges only ever go applicant-to-job, never applicant-to-applicant.

🎨 THE TWO-COLOR TEST

Checking bipartiteness is just a BFS/DFS coloring exercise: color the start node red, color every neighbor blue, every neighbor-of-neighbor red, alternating strictly. If you ever try to color a node a color it's already been assigned the opposite of, the graph isn't bipartite — you've found an odd-length cycle, which is provably the only thing that can break this alternating pattern (an even cycle alternates perfectly back to its start color; an odd cycle forces a contradiction on the last edge).

Bipartite matching asks: what's the maximum number of applicant-job pairs you can form, with each applicant getting at most one job and vice versa? The classic algorithm augments one match at a time using an "augmenting path" — alternating between unmatched and matched edges, and if you find a path from an unmatched applicant to an unmatched job, flipping every edge along that path (matched becomes unmatched, unmatched becomes matched) increases the total match count by exactly one.

🧠 WHY FLIPPING AN AUGMENTING PATH ALWAYS INCREASES THE MATCH COUNT

An augmenting path alternates unmatched, matched, unmatched, matched, ..., unmatched — starting and ending on unmatched edges, meaning it always has exactly one more unmatched edge than matched edges. Flipping every edge's status along this path turns every previously-unmatched edge into matched and vice versa — since there was one extra unmatched edge, the flip produces a net gain of exactly one matched edge overall, with everything else in the graph completely undisturbed. Repeating this — find an augmenting path, flip it — until no augmenting path can be found any longer, is provably guaranteed (by König's theorem, beyond this book's scope to fully prove) to reach the true maximum matching.

19.4Max Flow — the water pipe network

How much can actually get from source to sink

+

Given a directed graph where every edge has a capacity (like a pipe's maximum water throughput), and a designated source and sink, what's the maximum total flow that can travel from source to sink without exceeding any edge's capacity?

💧 THE FORD-FULKERSON "KEEP FINDING A PATH WITH ROOM" IDEA

Repeatedly find any path from source to sink that still has spare capacity somewhere along its whole length (the path's total extra capacity is limited by its bottleneck — the single skinniest pipe along the way), and push flow equal to that bottleneck through the entire path. The genuinely clever part: also add a "residual" reverse edge along the same path, letting a future path undo part of an earlier flow decision if a better overall arrangement is later discovered — this residual-edge trick is precisely what prevents the algorithm from getting permanently stuck on an early, suboptimal set of choices. Repeat until no path with any spare capacity exists at all — at that point, the total flow pushed is provably the maximum possible (the max-flow min-cut theorem: the maximum flow always exactly equals the capacity of the smallest "cut" — the cheapest possible set of edges whose removal would fully disconnect source from sink).

✅ WHY THIS SHOWS UP MORE OFTEN THAN "PIPE NETWORK" PROBLEMS SUGGEST

Max flow is a genuinely surprising Swiss-army-knife: bipartite matching (Section 19.3) is literally a special case of max flow (connect a source to every applicant, every job to a sink, capacity 1 on every edge). Many "assignment" or "scheduling under constraints" problems that don't look like flow at all can be reframed as one, which is exactly why recognizing the shape — "can I model this as capacities flowing from a source to a sink" — is worth having as a mental tool, even without implementing a full flow algorithm from scratch under interview time pressure.

19.5Where smart people trip up

+
⚠️ Forgetting to skip the immediate parent edge in bridge-finding

Without excluding the edge back to the direct parent, every tree edge would incorrectly look like a back edge to itself, making low[u] artificially small and hiding every real bridge and articulation point.

⚠️ Confusing Kosaraju's finish-time order (need reverse) with a plain topological sort order

The two look superficially similar (both use DFS finish times) but Kosaraju's second pass specifically needs the graph's edges reversed — running the second DFS on the original graph instead silently produces wrong SCC groupings.

⚠️ Assuming any two-coloring attempt failing means "no bipartition exists anywhere," rather than checking each connected component separately

A disconnected graph can have some components that are bipartite and others that aren't — always check per-component, not as one single global pass that might incorrectly abort on the first violation found in an unrelated part of the graph.

19.6Check your understanding

+
Q1 — Why is the bridge condition strictly ">" while the articulation point condition is ">="?›

A bridge requires the child's subtree to have absolutely no rope back to u or higher — even reaching u itself (equal, not just less) means there's still an alternate route through u, so the direct edge isn't the sole connection. An articulation point only requires that removing u specifically would disconnect the child — reaching exactly u (not past it) still means u itself is essential, satisfying the ">=" condition, even though the edge itself isn't uniquely essential.

Q2 — Why does an augmenting path in bipartite matching need to start and end on unmatched edges specifically?›

Starting and ending on unmatched edges is what guarantees the path has exactly one more unmatched edge than matched edges, which is precisely what makes flipping every edge's status a net gain of one match — a path with equal matched/unmatched counts, or starting/ending on matched edges, wouldn't produce this clean one-more-unmatched imbalance and wouldn't actually increase the total match count when flipped.

Q3 — Why does the residual reverse edge in max-flow matter — what would break without it?›

Without it, an early greedy flow decision could never be reconsidered — the algorithm could get permanently stuck sending flow along a path that blocks a better overall arrangement, with no mechanism to undo it. The residual edge lets a later path effectively "cancel" part of an earlier decision, which is exactly what's needed to guarantee the algorithm converges to the true global maximum rather than a locally-greedy, suboptimal flow.

These four ideas — bridges, SCCs, bipartite matching, max flow — are the graph techniques that separate "I know BFS/DFS" from "I can model a genuinely novel constraint problem as a graph." They're rarer in day-to-day interview questions than Chapter 14's core toolkit, but they're exactly what shows up when a problem doesn't fit any of the standard shapes.
