CHAPTER THREE OF TEN · INTUITION FIRST

Strings

Almost everything you already know about arrays carries straight over — strings are just arrays of characters. This chapter is really about the handful of places where that "just an array" story gets a plot twist, and the genuinely clever tricks (hashing, KMP, Manacher's) people invented to deal with those twists.

Builds directly on Chapter 2's array intuition

3.1A costume over an array

What's actually new here, and what genuinely isn't

+

Before anything clever, the honest starting point: a string is a sequence of characters sitting in memory, contiguous, indexed from 0 — which means everything from Chapter 2 about the "parking lot" applies without modification. s[3] is O(1) for the exact same reason arr[3] was. Looping through a string character by character is O(n), same as looping through an array. Reversing, searching, comparing two strings for equality — all of it is array logic wearing a costume made of letters instead of numbers.

So why does this topic deserve its own chapter at all, instead of just being a footnote on arrays? Because two specific properties of strings — being immutable in many languages, and being read and compared as whole meaningful chunks (words, patterns, palindromes) rather than just individual numbers — open up a set of problems and tricks that don't really have an array equivalent. That's what the rest of this chapter is actually about.

3.2The immutability trap

Revisiting Chapter 1's warning, but seeing exactly why it happens

+

Chapter 1 mentioned this as a pitfall in passing — here's the full picture. In many languages, once a string is created, it can never be changed in place. Every time you write something that looks like "add a character to this string," what's actually happening under the hood is: throw the entire old string away, allocate a brand new block of memory slightly bigger, and copy every old character into it plus the new one.

📜 THE STONE TABLET ANALOGY

Imagine a message carved into a stone tablet. You can't add a single letter to the end of it — stone doesn't work that way. If you want a message with one more letter, you have to carve an entirely new tablet, re-carving every existing letter from scratch, plus the new one at the end. That's exactly what "immutable string" means: every single change, no matter how small, means re-copying the whole thing onto a fresh tablet.

Now picture doing this in a loop, building up a string one character at a time:

result = ""
for ch in some_very_long_text:
    result = result + ch   # looks innocent — is secretly re-carving the whole tablet

On iteration 1, you re-carve a tablet of length 1. On iteration 2, a tablet of length 2. By iteration k, you're re-carving a tablet of length k. This is exactly the triangle-loop shape from Chapter 1.4 — total re-carving work is 1 + 2 + 3 + ... + n ≈ n²/2. A loop that visually looks like a single, innocent O(n) pass has secretly become O(n²), purely because of this hidden re-copying cost baked into every "+".

✅ THE FIX, AND WHY IT ACTUALLY WORKS

Instead of carving a new tablet on every single letter, collect the letters in a mutable container (a list, an array of characters) — appending to a list at the end is O(1) amortized, exactly like Chapter 1.7's dynamic array doubling — and only carve the final stone tablet once, at the very end, by joining everything together in a single pass. One re-carve of the final length n, instead of n re-carves of growing length — collapsing O(n²) back down to the honest O(n) the loop looked like it deserved in the first place.

3.3Hashing — the fingerprint trick

How to compare huge chunks of text without reading all of it, every time

+

Here's a problem that shows up constantly: you have a huge amount of text, and you keep needing to ask "is this particular stretch of characters equal to that other stretch?" Character-by-character comparison works, but it's slow if you're asking this question over and over, especially on long stretches.

👆 THE FINGERPRINT ANALOGY

Imagine you're a detective trying to figure out if two people at a crime scene are actually the same person. You could stand them side by side and compare every visible feature, one by one — but a much faster shortcut, if you already have a fingerprint database, is to just compare their fingerprints: two short numbers. If the fingerprints match, you're very confident (though not mathematically 100% certain — fingerprints could theoretically collide) that they're the same person, without ever comparing their actual faces feature-by-feature. A hash is exactly this: a short, quickly-computed "fingerprint" for a much longer piece of text, letting you compare fingerprints instead of doing a full character-by-character comparison every time.

A simple way to build this string fingerprint: treat the string as a number in some base b (bigger than the size of your alphabet), where each character contributes a digit:

hash(s) = s[0]·b^(k-1) + s[1]·b^(k-2) + ... + s[k-1]·b^0
// exactly like how the number "present at a specific" present value comes from each digit times a power of 10 — just swap base 10 for base b, and digits for characters

Two different strings can, in rare unlucky cases, produce the exact same fingerprint — this is called a hash collision, and it's the honest asterisk on this whole technique: a fingerprint match is strong evidence of equality, not an absolute guarantee, unless you follow it up with a real character-by-character check to confirm (which, importantly, you only need to do on the rare occasions the fingerprints actually match — not on every comparison).

3.4Rabin-Karp — sliding the fingerprint

Finding a pattern inside a big text, using the fingerprint trick as you slide along

+

The problem: find every place a short pattern (say, a 5-letter word) appears inside a much longer text. The naive way — try matching the pattern starting at every single position in the text, comparing letter by letter each time — costs roughly O(n·m), where n is the text length and m is the pattern length, because in the worst case you re-compare almost the whole pattern at almost every starting position.

Rabin-Karp's insight: instead of re-comparing letters from scratch at every position, compute the fingerprint of the pattern once, then slide a same-sized window across the text, and instead of recomputing that window's fingerprint from scratch each time, update it incrementally — a genuine O(1) update per slide, not a full recompute.

🎞️ THE FILM-STRIP WINDOW ANALOGY

Picture holding a small cardboard window over a long strip of text, showing only 5 letters at a time, and sliding that window one letter to the right at each step. Instead of re-reading and re-summing all 5 visible letters every single time you slide (wasteful — 4 of the 5 letters didn't even change!), you can be clever: subtract out the contribution of the letter that just left the window on the left, shift everything else's "place value" over by one (multiply by the base), and add in the contribution of the new letter that just entered on the right. Three quick arithmetic operations, regardless of how wide the window is — genuinely O(1) per slide, instead of re-summing the whole window.

new_hash = (old_hash − leaving_char × b^(m-1)) × b + entering_char
// remove the leaving character's contribution, "shift" everyone else up one place value, add the entering character

At every window position, compare the window's fingerprint against the pattern's fingerprint — an O(1) check — and only bother doing an actual full character-by-character confirmation on the rare occasions the fingerprints happen to match (guarding against the collision risk from the last section). Sliding across the whole text costs O(n) total slides, each O(1) — genuinely O(n+m) on average, a real improvement over the naive O(n·m), achieved purely by refusing to redundantly re-read overlapping parts of the window on every slide, in the same spirit as Chapter 2's prefix sums refusing to re-sum overlapping ranges.

3.5KMP — never forget what you already know

Pattern matching that never backtracks through the text itself

+

KMP solves the same problem as Rabin-Karp — find a pattern inside a text — but with a completely different, and genuinely elegant, idea: what if, on a mismatch, we could figure out exactly how far to jump the pattern forward, using information the pattern already told us about itself, instead of naively sliding forward by just one position and starting the comparison completely over?

🧩 THE "DON'T FORGET WHAT YOU ALREADY KNEW" ANALOGY

Imagine you're matching the pattern "ABABC" against some text, and you've successfully matched "ABAB" before hitting a mismatch on the 5th character. Naive matching would throw away all of that hard-won progress and restart the entire comparison from the very next position in the text, character by character, as if you'd learned nothing. But think about what you actually do know at this point: the last 4 matched characters were "ABAB" — and you can look at the pattern itself and notice that "AB" (the first 2 characters) is also a suffix of what you just matched. That means you don't need to re-check those 2 characters at all when you shift the pattern forward — you already know, for free, purely from the pattern's own internal structure, that they'll match. You only need to resume checking from where your actual new information runs out.

This "how much of what I just matched can I keep, for free, based on the pattern's own structure" is precomputed once per pattern into something called the LPS array (Longest Prefix which is also a Suffix). LPS[i] tells you: for the pattern's first i+1 characters, what's the length of the longest proper prefix that's also a suffix of that same chunk? This is purely a property of the pattern itself — it has nothing to do with the text you're searching, which is exactly why it can be computed once, upfront, and reused throughout the entire search.

pattern = "ABABC"
LPS     =  [0, 0, 1, 2, 0]
# LPS[3] = 2 means: the first 4 characters "ABAB" have a matching
# 2-character prefix-and-suffix, namely "AB" — so on a mismatch right
# after matching "ABAB", we can safely skip re-checking those 2 letters
🧠 WHY THIS MAKES THE WHOLE SEARCH GENUINELY O(n+m), NOT JUST "USUALLY FASTER"

The crucial, provable guarantee: the pointer walking through the text never, ever moves backward — it only ever advances forward, one character at a time, for the entire search. Only the pointer walking through the pattern ever jumps backward, and it does so using the precomputed LPS table rather than blindly restarting. Because the text pointer makes at most n forward moves total, and the pattern-building step (computing the LPS array itself) is a separate, one-time O(m) cost, the whole search is a clean O(n + m) — genuinely guaranteed, not just a lucky average case the way Rabin-Karp's hashing approach technically is (Rabin-Karp has a rare worst case where many collisions force it back toward O(n·m); KMP has no such asterisk).

3.6The Z-function, briefly

A close cousin of KMP's idea, framed slightly differently

+

The Z-function asks a subtly different question than LPS did: for every starting position i in a string, how long is the stretch starting at i that matches the very beginning of the string? Call this Z[i].

🪞 THE "HOW FAR DOES THIS ECHO THE OPENING" ANALOGY

Imagine reading a long string and, starting from every single position, asking "if I compare what follows from here against the string's very own opening, how far do they stay identical before diverging?" That "how far before diverging" number, recorded at every starting position, is the entire Z-function.

The clever trick that makes this computable in O(n) total, rather than restarting the comparison from scratch at every position (which would be O(n²)): once you've discovered a matching stretch, you remember its boundaries (call them [l, r], the rightmost match-window found so far), and for any new position that falls inside that already-explored window, you can often reuse previously-computed Z-values instead of blindly re-comparing character by character — the exact same "don't forget what you already know" spirit as KMP's LPS array, just applied to a slightly different question.

Practically, this shows up most often for pattern matching by gluing the pattern and text together with a separator character not found in either (pattern + "#" + text), then computing the Z-function of that combined string — any position where Z[i] equals the pattern's length marks a genuine match. Worth knowing this exists and roughly why it works, more than memorizing its exact implementation cold — KMP is the more commonly reached-for tool for straightforward pattern matching, and the Z-function tends to show up when a problem needs this "match against the opening" framing specifically.

3.7Palindromes and Manacher's mirror trick

Finding the longest palindrome without checking every possible substring

+

A palindrome reads the same forwards and backwards — "racecar," "level," "noon." The brute-force way to find the longest palindromic substring inside a bigger string is to check every possible substring (an O(n²) count of them, the familiar triangle shape) and, for each, verify it's a palindrome (another O(n) check) — a costly O(n³) altogether, or O(n²) with a smarter "expand outward from each center" approach. Manacher's algorithm gets this all the way down to O(n), using a genuinely beautiful trick worth actually seeing.

🪟 THE HALL-OF-MIRRORS ANALOGY

Imagine you're standing inside a large palindrome — think of it as a hallway with a mirror at its exact center, where the left half is a perfect reflection of the right half. Now suppose you've already carefully measured how far a smaller palindrome extends, somewhere on the left side of this hallway. Here's the beautiful realization: because the whole hallway is mirror-symmetric around its center, there must be a matching palindrome on the right side too, at the mirrored position, extending out to at least the same distance — you don't have to re-measure it from scratch by expanding outward character by character. You can just glance at its mirror-image twin's measurement and start from there, only doing fresh, careful expansion-checking once you run past the boundary of the big hallway-palindrome where the mirror guarantee stops applying.

Concretely: Manacher's algorithm keeps track of the rightmost-reaching palindrome discovered so far and its center. For each new position, if it falls inside that current rightmost palindrome's reach, it initializes its own palindrome-radius using its already-computed mirror-twin's radius (capped appropriately at the boundary) before doing any fresh character comparisons — meaning a huge amount of potential re-checking gets skipped entirely, purely by exploiting symmetry that's already been discovered. Only once you're forced past the known boundary do you fall back to genuinely fresh, character-by-character expansion.

🧠 WHY THIS COLLAPSES ALL THE WAY TO O(n)

The honest amortized argument, in the same spirit as Chapter 1's monotonic stack and Chapter 2's cyclic sort: the "rightmost boundary discovered so far" only ever moves forward, never backward, across the entire run of the algorithm — and every unit of genuinely fresh character-comparison work directly extends that boundary further to the right. Since the boundary can only move forward at most n times total, the total amount of fresh comparison work across the whole algorithm is bounded by O(n), even though any single position might occasionally trigger a burst of comparisons. The mirror trick isn't cutting corners on correctness — it's precisely avoiding redoing comparisons whose answers were already fully determined by symmetry.

3.8Anagrams — the fingerprint, reused

A much simpler idea than it sounds, once you see the connection

+

Two words are anagrams if one is just a rearrangement of the other's letters — "listen" and "silent," for instance. How do you check this without trying every possible rearrangement (which would be a genuinely awful O(n!) approach)?

🧺 THE INGREDIENT-BASKET ANALOGY

Imagine each word is a basket of scrabble tiles. Two baskets contain "the same word, rearranged" precisely when they contain the exact same tiles in the exact same quantities — it genuinely doesn't matter what order the tiles sit in inside the basket. So instead of comparing the words letter-position by letter-position (which cares about order, and is the wrong question entirely), just count how many of each letter is in each basket, and compare those two counts. If the counts match exactly, letter for letter, the baskets are anagrams — full stop, order never even enters into it.

Practically: build a frequency count (an array of size 26 for lowercase English letters is enough — no hash map even needed, since the "address" for each letter's count is just its position in the alphabet, a nice callback to Chapter 2's cyclic sort idea of "the value tells you its own address"), incrementing for one word and decrementing for the other as you walk through both. If you land back at all-zeros, the counts matched perfectly, and they're anagrams.

counts = [0] * 26
for ch in word1: counts[ord(ch) - ord('a')] += 1
for ch in word2: counts[ord(ch) - ord('a')] -= 1
return all(c == 0 for c in counts)

This is genuinely the same underlying idea as Section 3.3's fingerprint trick, just wearing yet another costume: instead of comparing two long words character by character in order (an ordered comparison), you're compressing each word down into a short, order-independent "fingerprint" — its letter-frequency signature — and comparing those instead. Two words with matching frequency signatures are guaranteed anagrams, with none of the "rare collision" asterisk that plain numeric hashing carried, since a full 26-length frequency count carries exactly as much information as the original word's letter multiset, no compression loss at all.

3.9Where smart people trip up

String-specific mistakes, explained through why the confusion happens

+
⚠️ MISTAKE 1 — Trusting a hash match without ever confirming it

It's tempting, once you've built a fast fingerprint check, to treat a fingerprint match as absolute proof of equality and skip verification entirely. But remember: hash collisions, while rare, are mathematically possible — two genuinely different strings landing on the same fingerprint by unlucky coincidence. For correctness-critical code (not just "probably fine" code), always follow up a hash match with a real character-by-character confirmation, especially in an adversarial setting where someone might deliberately try to engineer a collision.

⚠️ MISTAKE 2 — Forgetting the multiplier when removing the leaving character in a rolling hash

In Rabin-Karp's sliding update, it's easy to forget that the leaving character's contribution needs to be multiplied by b^(m-1) before subtracting — because that character was sitting at the most significant place-value position in the window, not the least significant one. Forgetting this power term is a common, subtle bug that silently produces wrong fingerprints rather than an obvious crash, since the arithmetic still "runs," it just computes the wrong number.

⚠️ MISTAKE 3 — Confusing "prefix that's also a suffix" with "any matching substring"

KMP's LPS array specifically wants the longest proper prefix (not the whole string itself) that's also a suffix of the same chunk — it's easy to accidentally include the full string as its own "prefix-suffix match," which breaks the whole algorithm's logic, since that would mean "skip past everything," which makes no sense for finding a genuine mismatch-recovery jump. Always double check the LPS table by hand on a short 4-5 character example before trusting a general implementation.

⚠️ MISTAKE 4 — Assuming Unicode/multi-byte characters behave like single array cells

In some languages and encodings, a single visible character (especially emoji, or characters outside basic ASCII) can actually be represented internally by more than one underlying storage unit. This quietly breaks the "parking lot" assumption from Chapter 2 that every cell is the same fixed size — s[i] might land you in the middle of a multi-unit character rather than cleanly on a character boundary. Worth being aware this asterisk exists, even if most interview-style problems conveniently stick to plain ASCII to sidestep it.

3.10Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Why does result = result + ch inside a loop secretly cost O(n²), using the stone tablet picture?›

Because strings are immutable — every "+" doesn't add a letter to the existing tablet, it re-carves an entirely new, slightly longer tablet from scratch. On iteration k, you're re-carving a tablet of length k, so total re-carving work across n iterations is 1+2+...+n ≈ n²/2 — the same triangle-loop shape from Chapter 1. It's an invisible cost hidden behind an innocent-looking "+" operator.

Q2 — In your own words, what does a hash collision mean, and why doesn't it make hashing useless?›

A collision is when two genuinely different strings happen to produce the exact same fingerprint by unlucky coincidence — like two different people accidentally sharing a fingerprint pattern in a flawed database. It doesn't make hashing useless because collisions are rare with a well-chosen hash, and you can always follow up a fingerprint match with a real full comparison to confirm — you're using the fast fingerprint check to quickly rule out the overwhelming majority of non-matches, then paying the full comparison cost only on the rare occasions it's actually needed.

Q3 — What's the core idea KMP and the Z-function actually share, even though they compute slightly different things?›

Both refuse to "forget" information the string has already revealed about its own structure, and both reuse that information to skip redundant future comparisons instead of naively restarting from scratch after every mismatch or at every new position. KMP asks "how much of what I just matched can I keep on a mismatch" using the pattern's own prefix-suffix structure; the Z-function asks "how far does this position echo the opening" using previously-discovered match windows. Different questions, same underlying "don't redo work whose answer you already know" spirit.

Q4 — Using the hall-of-mirrors picture, explain why Manacher's algorithm doesn't need to re-verify every mirrored palindrome from scratch.›

Because the region inside the currently-known rightmost palindrome is genuinely, provably mirror-symmetric — whatever palindrome radius was measured on the left side is guaranteed to exist at the mirrored position on the right side too, as a direct consequence of the bigger palindrome's own symmetry, not a guess or heuristic. So that measurement can be reused as a starting point instead of re-measured from zero — fresh character comparison is only needed once you go past where the mirror guarantee runs out, at the boundary of the currently-known palindrome.

Q5 — Why is checking anagrams via letter-frequency counting fundamentally different from checking two strings for exact equality character-by-character?›

Exact equality cares about both which characters appear and the precise order they appear in. Anagram-checking only cares about which characters appear and how many of each — order is completely irrelevant, like comparing scrabble-tile baskets rather than comparing two written-out words position by position. Frequency counting throws away order entirely and compares only the "ingredient list," which is exactly the right compression for a question that was never about order in the first place.

Q6 — Rabin-Karp and KMP both solve "find pattern in text" in roughly linear time. Why might you still prefer one over the other?›

KMP has a genuinely guaranteed O(n+m) worst case, no asterisks — its correctness doesn't depend on luck. Rabin-Karp's O(n+m) is an average-case story; in a rare, unlucky (or adversarially engineered) situation with many hash collisions, it can degrade back toward O(n·m) from all the fallback full comparisons. On the other hand, Rabin-Karp's rolling-hash idea generalizes more naturally to problems like "find any of many patterns at once" or 2D pattern matching, where KMP's specific prefix-suffix machinery doesn't extend as cleanly. Pick based on which property — guaranteed worst case, or easy generalization — matters more for the specific problem in front of you.

Nearly every trick in this chapter is the same move as Chapter 2's, just aimed at text instead of numbers: find some structure already sitting inside the data (a mirror symmetry, a repeated prefix, a frequency signature) and reuse it instead of redoing work whose answer you already, secretly, know.
