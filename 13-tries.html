Tries

A trie answers a question hash sets are structurally incapable of answering well: not "does this exact word exist," but "does anything start with these letters." That's a genuinely different question, and it needs a genuinely different shape of structure.

Builds directly on Chapter 2's "the value tells you its own address" idea

13.1The question a hash set can't answer

Why "starts with" is a fundamentally different kind of question than "equals"

+

A hash set is genuinely excellent at one specific question: "is this exact word in my collection?" O(1) average, done. But ask it a subtly different question — "does any word in my collection start with 'pre'?" — and it has no good answer at all. It would have to check every single stored word, one at a time, seeing if each one happens to start with "pre" — a full O(n) scan, with the hashing that made exact lookups fast offering no help whatsoever here.

🗄️ WHY HASHING ACTIVELY WORKS AGAINST PREFIX QUESTIONS

A hash function is deliberately designed to scatter similar-looking inputs into wildly different, unrelated storage locations — that scattering is exactly what prevents collisions and keeps lookups fast. But that same scattering is precisely what destroys any useful relationship between "predict" and "prefix" and "president" — even though they all start with "pre," a hash function will happily send them to three completely unrelated corners of memory, with nothing connecting them. The property that makes hashing good at one job (exact lookup) is the very same property that makes it bad at the other (prefix lookup) — it's not a missing feature, it's a direct structural consequence of what hashing is built to do.

A trie is built specifically to make "starts with" cheap, by doing the opposite of hashing: instead of scattering similar inputs apart, it deliberately merges them together wherever they share a common beginning.

13.2A hallway that forks at every letter

The actual shape of the structure, built up from the problem it solves

+
🚪 THE FORKING-HALLWAY ANALOGY

Imagine a building where you enter through a single front door, and every hallway forks at every single letter of every word stored inside. Walking down the hallway spelling out "c-a-t" means you pass through a fork for 'c', then a fork for 'a', then a fork for 't' — and if the building also contains the word "car," the "c" and "a" hallway segments are the exact same physical hallway as the beginning of "cat"'s path — they only diverge at the third letter, where one path continues to 'r' and the other to 't'. Words that share a prefix genuinely share hallway segments, right up until the point where their spellings actually differ.

insert("cat"), insert("car"), insert("dog") (root) / \ c d | | a o / \ | t r g * * * ← * marks "a complete word ends here"

Each node in this structure represents one character position along some path from the root, typically implemented as a dictionary or fixed-size array mapping "next character → next node," plus a flag marking whether a complete, valid word actually ends at this exact node (necessary because "car" being a word doesn't mean "ca" is also one — the flag distinguishes "a word ends here" from "this is merely a letter passed through on the way to a longer word").

🧠 WHY SHARED PREFIXES BEING PHYSICALLY MERGED IS THE ENTIRE POINT

This structural merging is precisely what makes "does anything start with X" cheap: walking the hallway for "ca" and checking whether that fork exists at all instantly tells you whether any stored word begins with "ca" — you never need to check "cat" and "car" and "cabbage" individually, because their shared beginning was only ever stored once, as one shared hallway segment. This is genuinely the same underlying idea as Chapter 2's cyclic sort and Chapter 9's monotonic stack — "don't redo or duplicate what's already implied by structure" — just expressed here as physically shared paths instead of avoided recomputation.

13.3Insert and search, walked through slowly

Both operations are the same hallway walk, differing only in what happens on a dead end

+
class TrieNode:
    def __init__(self):
        self.children = {}       # letter -> TrieNode
        self.is_end_of_word = False

def insert(root, word):
    node = root
    for ch in word:
        if ch not in node.children:
            node.children[ch] = TrieNode()   # build a new hallway fork
        node = node.children[ch]              # walk through it
    node.is_end_of_word = True            # plant a flag: a word ends exactly here

def search(root, word):
    node = root
    for ch in word:
        if ch not in node.children:
            return False              # hallway doesn't exist — dead end
        node = node.children[ch]
    return node.is_end_of_word         # hallway exists — but does a WORD end here?

def starts_with(root, prefix):
    node = root
    for ch in prefix:
        if ch not in node.children:
            return False
        node = node.children[ch]
    return True                     # hallway exists — that's ALL prefix-check needs
🧠 THE ONE-LINE DIFFERENCE THAT SEPARATES "SEARCH" FROM "STARTS_WITH" — WORTH GETTING EXACTLY RIGHT

Notice search and starts_with are almost character-for-character identical code, walking the exact same hallway — the entire distinguishing difference is the final return line. search needs the walked path to end exactly at a node flagged is_end_of_word, because "the hallway to 'ca' exists" does not mean "'ca' is itself a valid, complete word" (it might only exist because "cat" or "car" passes through it). starts_with only cares that the hallway exists at all — it never checks the flag, because a valid prefix doesn't need to itself be a complete word. This single-line distinction is the entire structural payoff of storing the end-of-word flag separately from "this node exists" in the first place.

All three operations cost O(L), where L is the length of the word or prefix being processed — genuinely independent of how many total words are stored in the trie, since you only ever walk one path down from the root, never touching any of the other branches. Compare this to Section 13.1's hash-set scan, which was O(n) — proportional to the number of stored words, regardless of how short the prefix being searched for was.

13.4Tries as a pruning device for backtracking

Combining this chapter with Chapter 7, for a genuinely powerful payoff

+

A classic, genuinely instructive problem: given a grid of letters and a dictionary of valid words, find every word from the dictionary that can be traced out by a path of adjacent letters in the grid. The natural approach is Chapter 7's backtracking — explore every possible path letter by letter — but without help, this explores an enormous number of paths that are doomed from the very first few letters.

🚧 CHAPTER 7's "DON'T WALK THE DEAD-END HALLWAY," NOW WITH A MAP IN HAND

Recall Chapter 7.4's pruning idea: don't fully explore a path once you can already tell it's doomed. The problem there was knowing a path was doomed without a fast way to check. A trie built from the dictionary is exactly that fast way to check: at every single step of the grid exploration, walk the corresponding hallway in the trie alongside it. The instant the trie hallway you'd need doesn't exist — meaning no dictionary word could possibly continue with the letters traced out so far — you know with total certainty that continuing to explore this specific grid path is hopeless, and you can abandon it immediately, without wasting any further exploration on it.

def backtrack(row, col, trie_node, path):
    ch = grid[row][col]
    if ch not in trie_node.children:
        return                          # no dictionary word can possibly continue this way — prune
    next_node = trie_node.children[ch]
    path.append(ch)
    if next_node.is_end_of_word:
        record(''.join(path))
    for neighbor in adjacent_cells(row, col):
        backtrack(neighbor.row, neighbor.col, next_node, path)
    path.pop()                             # Chapter 7's undo step, unchanged
🧠 WHY THE TRIE SPECIFICALLY, AND NOT JUST A PLAIN SET OF WORDS, IS WHAT MAKES THIS PRUNING POSSIBLE

This is worth being precise about, because it's the entire reason this chapter and Chapter 7 combine so well: a plain hash set of dictionary words could only ever tell you "is the path traced so far a complete, valid word" — it has no way to answer the genuinely different, and far more useful, mid-search question "could this partial path still possibly become some valid word if I kept going?" A trie answers exactly that second question, for free, as a direct structural side effect of Section 13.1's prefix-merging — the very thing that made "starts with" cheap for a static dictionary is precisely what makes "is this partial path still alive" cheap to check at every single step of a live, in-progress search.

13.5The honest cost — memory

Every trade-off in this book has an asterisk, and this one is worth naming plainly

+

Following Chapter 2.2's honest framing — nothing is free — it's worth being direct about what a trie costs in exchange for its fast prefix operations: memory, and often more of it than people expect at first.

⚠️ THE HONEST TRADE, NAMED PLAINLY

Every single character of every stored word potentially needs its own node, and every node potentially needs room for many possible next-character branches (up to 26 for lowercase English, far more for full Unicode) — and crucially, most of those possible branches sit unused (null or absent) at any given node, since most letters don't actually have every other letter following them in real words. This can add up to genuinely more total memory than simply storing the raw words themselves in a plain list or hash set would need, especially when the stored words don't share many common prefixes with each other — the structural benefit (shared hallways) only pays off in proportion to how much genuine overlap actually exists in the data.

This is exactly why a trie is a specialist tool, reached for specifically when prefix-based operations (autocomplete, "starts with" queries, the trie-plus-backtracking pruning from Section 13.4) are genuinely part of what's being asked — not a default, drop-in replacement for a hash set whenever strings are involved. If the actual questions being asked are all exact-match ("is this exact word present"), a hash set remains the leaner, more appropriate choice, and reaching for a trie there would be paying a real memory cost for a prefix capability that's never actually used.

13.6Where smart people trip up

Explained through why the confusion happens

+
⚠️ MISTAKE 1 — Confusing "the path exists" with "a word ends here"

Section 13.3's core distinction, worth restating directly as the warning it is: forgetting to check is_end_of_word in search (or accidentally checking it in starts_with, where it's not needed) is one of the most common trie bugs — it silently reports "cat" as a valid stored word just because the hallway to it exists, even if only "catastrophe" was ever actually inserted and "cat" itself never was.

⚠️ MISTAKE 2 — Reaching for a trie by default whenever a problem involves strings

Section 13.5's honest memory cost is exactly why this default instinct is worth resisting. If the actual operations needed are all exact-match lookups, a plain hash set is leaner and simpler — a trie earns its keep specifically when prefix-based questions ("does anything start with X," "what are all words starting with X," or Section 13.4's live-search pruning) are genuinely part of the problem, not just because the data happens to be strings.

⚠️ MISTAKE 3 — Forgetting to prune the trie-plus-backtracking search when a branch is exhausted

In Section 13.4's word-search combination, once a particular trie branch has yielded all the words it's going to (or was never going to yield any), continuing to explore grid paths that lead into that same dead branch repeatedly wastes work. A further, genuinely valuable optimization (worth knowing exists, even if not implementing it every time) is removing a trie node once it's been fully "used up" — no children left, and no longer marking any live word — so future searches passing through that same grid region prune even faster on subsequent encounters.

⚠️ MISTAKE 4 — Assuming trie operations are O(1) rather than O(L)

It's tempting, after hearing "independent of the number of stored words," to round that up to "constant time" — but the cost genuinely does depend on L, the length of the word or prefix being processed, which is not itself a constant across different queries. For most everyday words this difference is negligible in practice, but it's worth stating the complexity precisely as O(L) rather than O(1), especially if a problem involves unusually long strings where L could meaningfully dominate the cost.

13.7Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Why does the exact property that makes hashing fast for exact-match lookups (scattering similar inputs apart) make it useless for prefix questions?›

Hashing deliberately scatters inputs to avoid collisions and keep lookups fast, which means words sharing a prefix (like "predict" and "prefix") end up in completely unrelated storage locations with no structural connection between them. A prefix question needs exactly the opposite property — the ability to find everything sharing a beginning — which requires related inputs to be grouped or connected somehow, the direct opposite of what a hash function is designed to do.

Q2 — Using the forking-hallway picture, explain why storing "cat" and "car" in the same trie uses less total space than storing them completely separately.›

Both words share the same first two letters, "c" and "a" — in a trie, this shared beginning is walked through the exact same two nodes for both words, only forking into separate paths at the third letter where they actually differ ('t' versus 'r'). The shared prefix is physically stored once, not duplicated for every word that happens to share it, which is exactly why words with a lot of common prefixes benefit the most from this structural merging.

Q3 — What's the exact difference in what search() and starts_with() need to check, given they walk the identical hallway?›

Both need the hallway (the sequence of character-nodes) to exist all the way through — if any letter's fork is missing, both immediately fail. But search() additionally needs the final node reached to be flagged is_end_of_word, since a hallway existing only means some longer word passes through that point, not that the exact queried word was itself ever inserted. starts_with() doesn't check that flag at all — a valid prefix is allowed to not be a complete word on its own.

Q4 — In the word-search-with-backtracking combination, what specific question does the trie answer that a plain hash set of dictionary words couldn't answer?›

A plain hash set can only answer "is the path traced so far a complete valid word" — it has no way to answer "could this partial, in-progress path still possibly extend into some valid word." The trie answers that second, genuinely more useful question for free, because checking whether the next letter's hallway fork exists directly tells you whether any dictionary word could still possibly continue this way — exactly what's needed to prune a doomed grid-exploration path immediately, rather than only discovering it's doomed after fully tracing it out.

Q5 — Why isn't a trie automatically the better choice whenever a problem involves storing and looking up strings?›

A trie's fast prefix operations come at a genuine memory cost — potentially one node per character with room for many possible branches, most of them unused at any given node — which can add up to more total memory than simply storing the raw words in a hash set, especially when the stored words don't share much overlap with each other. If the actual operations needed are only exact-match lookups, that memory cost buys a prefix capability that's never used, making a plain hash set the leaner, more appropriate choice instead.

Q6 — Why is it more precise to describe trie operations as O(L) rather than O(1), even though they don't depend on how many words are stored?›

The cost genuinely scales with L, the length of the specific word or prefix being processed — walking a 3-letter hallway takes fewer steps than walking a 30-letter one, even though neither depends on the total number of other words stored in the trie. "Independent of the number of stored words" and "constant time regardless of everything" are two different claims — the operation is independent of one specific variable (word count), but it's not independent of L, which is why O(L) is the honest, precise complexity rather than O(1).

A trie is what you get when you take Chapter 2's "the value tells you its own address" idea and stretch it across an entire sequence of characters instead of a single number — every shared prefix becomes a shared, physically merged path, and that merging is simultaneously the whole benefit and the whole cost.
