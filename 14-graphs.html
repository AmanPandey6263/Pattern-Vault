14.1The friendship-map picture

What a graph actually is, and how to store one

+

Chapter 10's trees had one strict rule: every node has exactly one parent, no cycles. A graph drops that restriction entirely — any node can connect to any other node, in any pattern, with cycles allowed and no single "root" required at all. The simplest mental picture: a social network, where nodes are people and edges are friendships. Nothing says a friendship graph has to be hierarchical — your friend's friend can also be your own direct friend, forming a loop, and there's no natural "top" of the whole structure.

Edges can be directed (a one-way "follows" relationship, like on social media) or undirected (a mutual "friends" relationship), and can carry weights (a cost, distance, or strength associated with the connection) or not. These distinctions matter enormously for which algorithm applies — much of this chapter is organized around exactly these axes.

RepresentationSpace"Are u,v connected?""List u's neighbors"Best for
Adjacency matrixO(V²)O(1)O(V)dense graphs, frequent edge checks
Adjacency listO(V+E)O(degree)O(degree)sparse graphs — the default choice
💡 WHY ADJACENCY LIST IS THE DEFAULT, NOT THE MATRIX

Most real-world graphs are sparse — a social network with a million users doesn't have anywhere close to a million-squared friendships; most people know a tiny fraction of everyone else. An adjacency matrix would allocate space for every possible pair regardless, the overwhelming majority of it wasted on "no edge here" entries — genuinely the same wasted-space problem Chapter 12.7 flagged for tries when data doesn't share much structure. An adjacency list only stores edges that actually exist, which is why O(V+E) — not O(V²) — is the realistic cost for the graphs you'll actually encounter, and exactly why Chapter 6.4's honest habit of asking "what does my actual data look like" applies here too.

14.2Go deep first, or go wide first

Chapter 9's stack-versus-queue distinction, finally given its biggest stage

+

The two fundamental ways to explore a graph are exactly Chapter 9's two structures, applied to exploration order instead of raw storage.

🌀 THE MAZE-EXPLORER, TWO DIFFERENT STYLES

DFS (depth-first search) is Chapter 7's maze-with-a-pencil, precisely: commit to a direction, walk as far as that path allows, and only backtrack once you genuinely hit a dead end — using a stack (explicit, or implicitly via recursion's own call stack) to remember where to backtrack to. BFS (breadth-first search) is a completely different exploration style: imagine a search party spreading out from a starting point in expanding rings, fully exploring every location exactly one step away before advancing to anything two steps away — using a queue to guarantee this strict distance-by-distance ordering, since a queue only ever releases things in the order they arrived, which here means strictly in order of discovery distance.

# DFS — stack (or recursion)
def dfs(start):
    visited = {start}
    stack = [start]
    while stack:
        node = stack.pop()
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                stack.append(neighbor)

# BFS — queue
def bfs(start):
    visited = {start}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)

Both are O(V+E) — every vertex is visited once, and every edge is examined once (from whichever side reaches it first) — a direct echo of Chapter 9.1 and 9.2's picture of two structures sharing a common shape, differing only in one flipped ordering rule, with genuinely different consequences flowing from that single flip.

14.3Why BFS guarantees the shortest hop-count

Not a coincidence — a direct consequence of the queue's ordering rule

+

Here's a fact worth actually proving, not just accepting: in an unweighted graph, the very first time BFS reaches a node, it has necessarily done so via the shortest possible path (fewest edges) to that node. Why is this guaranteed, and not just usually true?

🧠 THE PROOF, BUILT FROM THE RING-EXPANDING PICTURE

BFS's queue enforces that every node at distance 1 from the start is fully discovered and processed before any node at distance 2 is even looked at, which is fully discovered before any node at distance 3, and so on — a direct, mechanical consequence of a queue only ever releasing what's been waiting longest. So by the time BFS ever gets around to discovering a node at distance k for the very first time, it has already, by construction, exhausted every possible path of length less than k. There is no way a shorter path could have been "missed" — the ring-by-ring discipline the queue enforces guarantees every shorter possibility was already checked and ruled out before this node was ever reached at all.

This is exactly why BFS, not DFS, is the standard tool for shortest-path questions on unweighted graphs — DFS's "commit to one direction and go deep" strategy offers no such distance guarantee at all; it might stumble onto a hugely roundabout path to a node long before ever trying the genuinely short, direct path.

14.4Cycle detection — two genuinely different questions

Why "directed" and "undirected" need different logic, not just a tweak

+

Detecting a cycle sounds like one problem, but directed and undirected graphs need genuinely different reasoning — conflating them is a common, subtle source of bugs.

Undirected: during a DFS, if you reach a node that's already visited and it isn't the node you just came from, you've found a cycle — walking back to your immediate parent is normal and expected (that's just the edge you arrived by, seen from the other side), not evidence of looping.

🧭 THE "AM I STILL ON MY OWN CURRENT PATH" QUESTION (DIRECTED)

Directed graphs need a subtler check. Picture DFS as one person walking a single trail, occasionally sending scouts down side trails, each scout reporting back before the main walker continues. A directed cycle means the current trail eventually loops back on itself — not that two different, unrelated scouts happened to both visit the same location, which is completely normal and harmless (many paths in a directed graph can converge on the same node without any cycle existing at all). The distinction that matters: is this "already visited" node still currently open on the path I'm actively walking right now, or was it visited and fully closed out by some earlier, now-finished scouting trip?

def has_cycle_directed(node, visiting, visited):
    visiting.add(node)              # mark: currently on MY active path
    for neighbor in graph[node]:
        if neighbor in visiting:
            return True            # looped back onto my own current path — real cycle
        if neighbor not in visited and has_cycle_directed(neighbor, visiting, visited):
            return True
    visiting.remove(node)           # done with this node's path — no longer "currently open"
    visited.add(node)               # permanently done, safe to revisit from elsewhere
    return False
🧠 WHY TWO SEPARATE SETS ARE NECESSARY, NOT REDUNDANT

This needs two genuinely different bookkeeping sets, not one — visiting (currently open, on the live path) and visited (permanently finished, safe to encounter again from any other direction). A single "have I seen this before" set, as sufficed for the undirected case, cannot distinguish "this node is part of my current active trail" from "this node was visited ages ago via a completely different, already-finished branch" — and that distinction is precisely what separates a genuine cycle from harmless convergence in a directed graph.

14.5Topological sort — the prerequisite chart

Ordering tasks so nothing is scheduled before its dependencies

+

Given a directed graph with no cycles (a DAG), a topological sort produces a linear ordering where every edge u→v places u before v — the natural picture is a university course catalog, where an edge "Calc I → Calc II" means Calc I must be scheduled before Calc II.

🎓 TWO GENUINELY DIFFERENT WAYS TO BUILD THE SCHEDULE

Kahn's algorithm (BFS-flavored): start by scheduling every course that has zero prerequisites — nothing is blocking them, so they're immediately safe to take. Once "taken," remove them from consideration, which might free up other courses whose only remaining prerequisite was exactly the one just completed. Repeat: schedule whatever's newly unblocked, remove it, repeat. DFS-flavored: fully explore each course's entire prerequisite chain first — you can't truly finish "Calc II" as a concept until you've fully traced out everything Calc II itself depends on — and only mark a course as "finished" (pushing it onto a result stack) once every one of its own dependencies has already been fully finished first. Reversing that finish-order stack at the end gives the valid schedule.

# Kahn's algorithm
in_degree = compute_in_degrees(graph)
queue = deque([n for n in graph if in_degree[n] == 0])
order = []
while queue:
    node = queue.popleft()
    order.append(node)
    for neighbor in graph[node]:
        in_degree[neighbor] -= 1
        if in_degree[neighbor] == 0:
            queue.append(neighbor)
# if len(order) < total nodes, a cycle exists — some courses could never unblock
🧠 WHY KAHN'S ALGORITHM ALSO DETECTS CYCLES, ESSENTIALLY FOR FREE

If a cycle exists somewhere in the graph, every course caught inside that cycle permanently depends, transitively, on another course that's also stuck inside the same cycle — none of them can ever reach an in-degree of zero, because completing any one of them requires completing another one first, in an unbreakable loop. This means the queue will run dry before every node has been scheduled — comparing the final order's length against the total node count is a direct, nearly-free byproduct check for exactly the kind of impossible, circular-dependency situation Section 14.4 was built to detect.

14.6Dijkstra — the spreading ink stain

Shortest paths with weights, and exactly where the greedy trust comes from

+

BFS finds shortest paths by hop-count, assuming every edge costs the same. Dijkstra's algorithm generalizes this to weighted edges (non-negative weights only — the reason why is the whole point of this section), always expanding toward whichever unvisited node is currently cheapest to reach, using Chapter 12's heap for O(1) access to that current cheapest candidate.

🖋️ THE SPREADING-INK-STAIN ANALOGY

Picture dropping ink onto the starting node and watching it spread outward through the graph's edges, where thicker (more expensive) edges let ink through more slowly than thin (cheap) ones. At any given moment, the very edge of the spreading stain represents the current frontier — and the point on that frontier the ink reaches next is, quite literally, whichever unstained node is currently closest (by total ink-travel cost) to the source. Dijkstra's algorithm just formalizes this: always expand to whichever unvisited node currently has the smallest known total distance from the start.

dist = {start: 0}
pq = [(0, start)]         # min-heap: (distance, node) — Chapter 12.5's pattern
while pq:
    d, node = heapq.heappop(pq)
    if d > dist.get(node, float('inf')):
        continue              # a cheaper route was already found — this entry is stale
    for neighbor, weight in graph[node]:
        new_dist = d + weight
        if new_dist < dist.get(neighbor, float('inf')):
            dist[neighbor] = new_dist
            heapq.heappush(pq, (new_dist, neighbor))
🧠 WHY THIS GREEDY EXPANSION IS PROVABLY SAFE — AND EXACTLY WHERE THAT SAFETY DEPENDS ON NON-NEGATIVE WEIGHTS

This is worth genuinely proving, echoing Chapter 16's upcoming theme of never trusting a greedy step without justification. When Dijkstra pops the current minimum-distance node off the heap, is it safe to consider that distance final, never to be improved later? Yes — provided all weights are non-negative — because any alternative path to that node would have to pass through some other, currently-unvisited node, and every unvisited node, by definition, already has a known distance at least as large as the one just popped (that's exactly why it wasn't popped first). Adding a non-negative edge weight on top of an already-at-least-as-large distance can only produce a total that's at least as large again — it can never sneak in below the distance already finalized. This chain of reasoning collapses instantly the moment negative weights are allowed: a currently-unvisited, seemingly-farther node could hide a large negative edge somewhere just past it, capable of producing a genuinely shorter total route that the greedy "finalize the current minimum" rule would have already locked out and never revisited. That single broken assumption is the entire reason Dijkstra requires non-negative weights, precisely and only.

14.7Bellman-Ford — patient, honest relaxation

Giving up Dijkstra's speed to genuinely handle negative weights

+

Bellman-Ford solves the exact problem Dijkstra can't: shortest paths when negative edge weights are allowed. Its core operation, "relaxation," is simple: for every edge u→v, check whether going through u offers a shorter route to v than whatever's currently known, and update if so.

🐢 THE "NEVER TRUST A DISTANCE UNTIL YOU'VE DOUBLE-CHECKED EVERYONE" ANALOGY

Where Dijkstra confidently declares a distance "final" the moment it's popped (a trust that Section 14.6 showed only holds for non-negative weights), Bellman-Ford refuses to trust anything as final until it has patiently rechecked every single edge, repeatedly, for long enough that no possible improvement could still be lurking somewhere unexamined. Specifically: any genuine shortest path in a graph with V vertices can use at most V-1 edges (a path revisiting a vertex would just be wasting steps, since you could always cut the loop out and get a shorter or equal path instead) — so relaxing every edge in the graph, V-1 times over, is provably enough rounds to guarantee every shortest path has been fully "discovered," however many edges it happens to use, up to that maximum.

dist = {node: float('inf') for node in graph}
dist[start] = 0
for _ in range(len(graph) - 1):        # V-1 rounds — provably sufficient
    for u, v, weight in all_edges:
        if dist[u] + weight < dist[v]:
            dist[v] = dist[u] + weight

# One MORE round — if anything still improves, a negative cycle exists
for u, v, weight in all_edges:
    if dist[u] + weight < dist[v]:
        print("negative cycle detected")
🧠 WHY A VALID DISTANCE THAT STILL IMPROVES ON ROUND V MEANS A NEGATIVE CYCLE, SPECIFICALLY

If V-1 rounds are provably enough to discover every genuine shortest path (since none can use more than V-1 edges), then any further improvement on an honest, extra Vth round can't be explained by a legitimately longer shortest path — there isn't one. The only remaining explanation is that some cycle in the graph has a net-negative total weight, meaning you could walk around that cycle infinitely, shaving a little more off the total distance every single lap, so no finite "shortest path" genuinely exists at all for nodes reachable through it. This is exactly why Bellman-Ford trades away Dijkstra's speed (O((V+E) log V) versus O(VE)) for something Dijkstra structurally cannot offer: a correctness guarantee even with negative weights, plus this clean, built-in negative-cycle detector.

14.8Floyd-Warshall — trying every waypoint

All shortest paths at once, via a genuinely clean recursive idea

+

Dijkstra and Bellman-Ford both find shortest paths from a single source. Floyd-Warshall answers a bigger question at once: shortest paths between every pair of nodes, simultaneously, using an idea that's genuinely a preview of Chapter 15's dynamic programming, worth flagging explicitly since you haven't formally met DP yet.

🛣️ THE "IS THERE A USEFUL DETOUR THROUGH HERE" QUESTION

The core idea: consider allowing paths to route through intermediate nodes, one at a time, in some fixed order — node 1 first, then node 2, then node 3, and so on. At each step, for every pair of nodes (i, j), ask one simple question: "would detouring through this newly-allowed waypoint k actually shorten the current best-known route from i to j?" If dist[i][k] + dist[k][j] beats the currently recorded dist[i][j], update it — you've just found a genuinely useful shortcut through k. Do this for every pair, for every waypoint, one waypoint fully processed before moving to the next.

dist = build_initial_distance_matrix(graph)   # direct edges only, infinity elsewhere
for k in range(n):              # the waypoint being newly allowed
    for i in range(n):
        for j in range(n):
            if dist[i][k] + dist[k][j] < dist[i][j]:
                dist[i][j] = dist[i][k] + dist[k][j]
🧠 WHY PROCESSING WAYPOINTS ONE AT A TIME, IN ORDER, IS WHAT MAKES THIS CORRECT

The subtle but crucial guarantee: by the time waypoint k is being considered, dist[i][k] and dist[k][j] already correctly reflect the shortest routes using only waypoints 1 through k-1 — so allowing k as a new option and checking whether it improves things is genuinely evaluating "is k, specifically, a useful new addition," never accidentally double-counting a route that already uses k internally in some other, not-yet-fully-processed way. This one-waypoint-at-a-time discipline, echoing Chapter 7's leap of faith (trust that everything processed so far is already correct, then extend it by exactly one new consideration), is what makes the whole O(V³) result correct rather than merely plausible-looking. O(V³) sounds worse than running Dijkstra from every single node separately (roughly O(V·(V+E)log V)) — but for dense graphs, or when the full all-pairs matrix is genuinely needed rather than just a handful of single-source queries, Floyd-Warshall's simplicity and clean handling of negative (non-cycle) weights make it the practical, honest choice.

14.9Minimum spanning trees — the cheapest bridges

Connecting everything as cheaply as possible, two different ways

+

Given a set of towns and the costs of building possible roads between them, a Minimum Spanning Tree connects every town using the cheapest possible total road cost, with no redundant loops (a tree, not a general graph — exactly Chapter 10's "no cycles" rule, applied here to a subset of edges chosen from a larger graph).

🌉 TWO HONEST WAYS TO BUILD THE CHEAPEST ROAD NETWORK

Kruskal's: sort every possible road by cost, cheapest first, and greedily build each one — unless it would connect two towns that are already connected through some other combination of roads already built (which would just be a wasteful, redundant loop). Prim's: start from a single town and grow one connected network outward, at every step adding whichever cheapest available road connects the current network to some town not yet reached — always growing the same single blob, rather than Kruskal's approach of considering all roads globally regardless of which specific blob they'd join.

🧠 WHY THE GREEDY "CHEAPEST FIRST" CHOICE IS PROVABLY SAFE HERE

This deserves the same scrutiny Chapter 16 will insist on for every greedy claim: why does always taking the globally cheapest available edge never backfire? Sketch of the reasoning: consider any valid spanning tree that supposedly doesn't include the single cheapest edge in the whole graph. Adding that cheapest edge into that tree would create exactly one cycle (since a tree plus any one new edge always creates exactly one cycle) — and removing any other edge from that newly-formed cycle instead gives back a valid spanning tree, but one that's now cheaper (or at worst equal), since every other edge in the graph costs at least as much as the cheapest one you just swapped in. This means any spanning tree that skips the cheapest edge can always be improved or matched by one that includes it — so it's never actually a strictly better choice to leave the cheapest edge out, which is exactly the "exchange argument" proof style Chapter 16 formalizes for greedy algorithms generally.

Kruskal's needs a fast way to check "are these two towns already connected through roads built so far" — which is precisely the job Section 14.10's Union-Find structure is built for, and the two are almost always taught and implemented together for exactly that reason.

14.10Union-Find — the conga line

Answering "are these connected" fast, without ever fully exploring the graph

+

Union-Find (Disjoint Set Union) tracks a collection of groups, supporting two operations: find(x) — which group is x currently in — and union(x, y) — merge x's group and y's group into one. It's the structure powering Kruskal's cycle check, and general undirected cycle detection as a clean alternative to Section 14.4's DFS-based approach.

👥 THE "EVERYONE POINTS TO THEIR GROUP LEADER" ANALOGY

Imagine every person in a group ultimately points, possibly through a chain of intermediaries, to a single agreed-upon group leader — find(x) means "follow x's pointer chain until you reach whoever it is that points to themselves," and that person is the leader, representing the whole group's identity. union(x, y) means finding both x's leader and y's leader, then having one leader publicly point to the other, merging the two groups into one under a single leader.

Done naively, this pointer-chasing can get slow if chains grow long — but two small, genuinely clever optimizations fix that entirely.

🧠 PATH COMPRESSION — THE "TELL EVERYONE THE SHORTCUT" TRICK

Every time find(x) walks a long chain to discover the leader, it can, on the way back, make every single node it just passed through point directly to that leader — flattening the chain permanently for every future lookup, instead of leaving the long chain in place to be re-walked every time. This is the exact same amortized spirit as Chapter 8.4's cycle-detection math: pay a little extra work once, and every future operation on that same chain gets cheaper as a direct, lasting result.

🧠 UNION BY RANK — THE "SMALLER GROUP JOINS THE BIGGER ONE" TRICK

When merging two groups, always have the smaller (or shorter) group's leader point to the bigger group's leader, never the reverse. Consistently attaching small trees under big ones, rather than risking the opposite, prevents any single chain from ever growing tall in the first place — a direct, structural echo of Chapter 10.6's balance obsession, just enforced through a merging rule instead of rotations.

parent = {x: x for x in nodes}   # everyone starts as their own leader
rank = {x: 0 for x in nodes}

def find(x):
    if parent[x] != x:
        parent[x] = find(parent[x])   # path compression — flatten on the way back
    return parent[x]

def union(x, y):
    root_x, root_y = find(x), find(y)
    if root_x == root_y:
        return False                   # already connected — this edge would form a cycle
    if rank[root_x] < rank[root_y]:
        root_x, root_y = root_y, root_x
    parent[root_y] = root_x            # smaller/shorter tree joins the bigger one
    if rank[root_x] == rank[root_y]:
        rank[root_x] += 1
    return True

Together, these two optimizations give near-constant O(α(n)) amortized cost per operation — the inverse Ackermann function, a quantity that grows so absurdly slowly it's effectively a small constant (under 5) for any n you'll ever encounter in practice, genuinely one of the most efficient amortized results in all of computer science.

14.11Where smart people trip up

Explained through why the confusion happens

+
⚠️ MISTAKE 1 — Running Dijkstra on a graph that might have negative weights

Section 14.6's entire proof of safety depended on non-negative weights — running Dijkstra anyway on a graph where negative weights are possible doesn't crash, it just silently produces a wrong, overly-optimistic-looking distance, since the greedy "finalize the current minimum" step is no longer actually justified. Always confirm weights are non-negative before reaching for Dijkstra; if they might not be, Bellman-Ford is the honest choice, even at the cost of speed.

⚠️ MISTAKE 2 — Using a single "visited" set for directed cycle detection

Section 14.4's core warning: undirected cycle detection can get away with one set, but directed cycle detection genuinely needs the two-set distinction (currently on my active path, versus permanently finished elsewhere) — using only one set will report false cycles on completely legitimate convergent paths that never actually loop back on themselves.

⚠️ MISTAKE 3 — Forgetting the "stale heap entry" check in Dijkstra

Because a node can be pushed onto the priority queue multiple times (once for every time a shorter route to it is discovered), popping an entry doesn't automatically mean it's still the best known distance for that node — some other, cheaper entry for the same node might already have been processed earlier. Skipping the if d > dist.get(node): continue check can lead to reprocessing a node with outdated, no-longer-optimal distance information, corrupting results built from it.

⚠️ MISTAKE 4 — Forgetting union by rank, and getting only half the Union-Find speedup

Path compression alone already helps enormously, but skipping union-by-rank (attaching arbitrarily, rather than consistently attaching the smaller tree to the larger one) can still let chains grow taller than necessary in adversarial insertion orders. Both optimizations together, not either alone, are what deliver the near-constant O(α(n)) guarantee.

14.12Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Using the expanding-rings picture, explain why BFS — not DFS — guarantees the shortest hop-count path.›

BFS's queue enforces that every node at distance k is fully processed before any node at distance k+1 is even examined — so the first time any node is ever reached, every shorter possible path to it has already, by construction, been checked and would have reached it first if it existed. DFS commits to one direction and goes deep, with no such distance-ordering guarantee at all — it can easily stumble onto a long, roundabout route to a node long before trying a genuinely short, direct one.

Q2 — Why does directed cycle detection need two separate sets, while undirected cycle detection only needs one?›

In a directed graph, reaching an already-visited node doesn't automatically mean a cycle — it might just be two separate, unrelated paths converging on the same node, which is completely normal. What actually matters is whether that node is still open on the specific path currently being walked, which requires tracking "currently active on my path" separately from "visited at some point, possibly via a different, already-finished branch." Undirected graphs don't have this convergence ambiguity in the same way — any repeated visit that isn't the immediate parent genuinely does indicate a cycle.

Q3 — In Dijkstra, why does the greedy "trust the current minimum as final" step break the instant negative weights are allowed?›

The safety argument relies on every unvisited node already having a distance at least as large as the one just finalized, and adding a non-negative weight on top of that can only make things at least as large again — never smaller. A negative edge breaks this completely: a currently-unvisited, seemingly-farther node could hide a large negative edge just beyond it, capable of producing a genuinely shorter total route that the algorithm would have already locked out and never gone back to reconsider.

Q4 — Why does an improvement on Bellman-Ford's extra, Vth round specifically indicate a negative cycle, rather than just a longer legitimate shortest path?›

Any genuine shortest path can use at most V-1 edges (revisiting a vertex would always be wasteful, since the loop could be cut out for an equal-or-shorter path), so V-1 rounds of relaxation are provably enough to discover every legitimate shortest path in the graph. If something still improves on a further, extra round, that improvement can't be explained by a legitimately longer path — the only remaining explanation is a cycle with negative total weight, which could be looped around indefinitely to keep "improving" the distance without limit.

Q5 — In Floyd-Warshall, why must waypoints be processed one at a time, in a fixed order, rather than all at once?›

By the time waypoint k is being considered, dist[i][k] and dist[k][j] need to already correctly reflect the best routes using only waypoints processed so far (1 through k-1) — this guarantees checking "does k help" is evaluating a genuinely new option, not accidentally relying on some other waypoint that hasn't been fully accounted for yet. Processing them out of order or all simultaneously would risk using partially-updated, not-yet-finalized distances, breaking the correctness of the whole accumulation.

Q6 — Using the exchange-argument sketch, explain why Kruskal's "always take the cheapest available edge" greedy rule is provably safe.›

Take any spanning tree that supposedly skips the single cheapest edge in the graph — adding that edge in creates exactly one cycle, and removing any other edge from that cycle instead restores a valid spanning tree that's now cheaper or equal, since every other edge costs at least as much as the one just swapped in. This means skipping the cheapest edge can never produce a strictly better tree than including it would — so it's always at least as good, and often better, to take the cheapest available edge whenever it doesn't create a cycle.

Graphs aren't really a new set of ideas — they're the reunion where Chapter 9's stack and queue, Chapter 12's heap, and the greedy-safety question first raised back in Chapter 6 all show up to the same problem at once. If those earlier chapters genuinely landed, this one is mostly recognition, not new invention.
