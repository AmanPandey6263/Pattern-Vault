17.1Numbers as light switches

The one picture that explains everything else in this chapter

+

Every integer your computer works with is, underneath, a row of light switches — each one either on (1) or off (0), and the specific pattern of on/off switches determines the number's value, exactly the same way a row of digits determines a value in ordinary base-10, just with only two possible states per position instead of ten.

This switch pattern (010100 read right to left as usual) represents the number 20 — the "on" switches are worth 16 and 4, and 16+4=20.

Once you hold this picture firmly — a number is a row of switches, not a mysterious abstract quantity — the operations in this chapter stop being arcane incantations and become genuinely readable statements about turning switches on, off, or checking their state, in bulk, all at once, across the entire row in a single instruction.

💡 WHY THIS CHAPTER'S TRICKS ARE WORTH KNOWING AT ALL

Because the computer can flip or check every switch in the row simultaneously, in a single operation, bit tricks are often dramatically faster than the equivalent loop-based logic — and, as Chapter 15.8 previewed, an entire row of switches can represent a whole set of up to 32 or 64 items, letting set operations (add, remove, check membership) become single, instant integer operations instead of anything resembling a loop at all.

17.2n & (n-1) — the domino trick

Why subtracting 1 has such a specific, useful ripple effect on the switches

+

One of the most quietly useful bit tricks: n & (n-1) always clears the lowest currently-on switch, leaving everything else untouched. Worth actually seeing why, not just memorizing.

🎲 THE ODOMETER-DIGIT DOMINO ANALOGY

Recall Chapter 1.7's odometer picture: subtracting 1 from a binary number causes a specific, predictable ripple — the lowest "on" switch flips off, and every switch below it (which must all currently be "off," since the lowest on-switch is by definition the lowest one that's set) flips on instead, exactly like an odometer rolling from ...1000 down to ...0111. Everything above that lowest on-switch stays completely untouched by the subtraction.

Now AND these two rows together — remember, AND only keeps a switch "on" in the result if it was on in both inputs. The lowest on-switch of n was off in (n-1), so it's cleared in the result. Everything below that switch was off in n to begin with, so ANDing changes nothing there either. Everything above that switch was identical in both n and (n-1) (the ripple never reached that far), so it's preserved exactly.

🧠 THE TWO CLASSIC USES THIS SINGLE FACT UNLOCKS

Repeatedly applying n = n & (n-1) in a loop, counting iterations until n reaches zero, counts exactly how many switches were originally on — each application removes precisely one, and only one, on-switch, giving an O(popcount) way to count set bits, genuinely faster than checking every one of the (potentially many more) total bit positions individually. And checking n & (n-1) == 0 (for n > 0) is an instant power-of-2 test — a power of 2 has, by definition, exactly one switch on, so clearing "the lowest on switch" clears the only on switch, leaving all zeros; any number with two or more switches on will still have at least one left after clearing just the lowest.

17.3n & (-n) — isolating one switch

A close cousin of the last trick, isolating rather than clearing

+

A related trick, n & (-n), isolates the lowest on-switch instead of clearing it — the result is a number with only that one switch on, everything else off. This relies on how negative numbers are actually represented: two's complement, defined as "flip every switch, then add 1."

🧠 WHY "FLIP EVERYTHING, THEN ADD 1" PRODUCES EXACTLY THE RIGHT SHARED BIT

Flipping every switch of n turns every originally-off switch on, and every originally-on switch off — including the lowest on-switch, which flips to off. Then adding 1 triggers Section 17.2's ripple exactly at that newly-off lowest position (since everything below it is now all "on," from the flip, and adding 1 to a run of all-1s ripples through exactly that run) — flipping that specific switch back on, and rippling everything below it back off, landing you right back at n's original lowest on-switch position, but now with everything else forced off by the flip that never got touched by this second ripple. The net result: -n shares exactly one "on" switch position with n — the original lowest one — and ANDing the two together isolates exactly that single shared switch.

This isolation trick shows up in structures like Fenwick trees (Binary Indexed Trees), where the lowest set bit of an index determines exactly which range of elements that index is responsible for summarizing — a genuinely elegant piece of engineering built directly on this exact bit fact, worth knowing exists even without full derivation here.

17.4XOR — the self-cancelling pair

The one operation whose "undo yourself" property does real work

+

XOR ("exclusive or") flips a switch if the corresponding input switch is on, and leaves it alone if it's off — check each position, and the output switch is on exactly when the two input switches disagree. The single most useful consequence of this rule: a ^ a = 0 (anything XORed with itself perfectly cancels to all switches off), and a ^ 0 = a (XORing with all-off switches changes nothing).

🔦 THE FLASHLIGHT-TOGGLE ANALOGY

Imagine a row of flashlights, and pressing a specific flashlight's button always toggles it — on becomes off, off becomes on. If you press the exact same sequence of buttons twice, every flashlight ends up back in its original state, because every toggle gets perfectly undone by its own repeat. XOR-ing a value with itself is exactly this — every switch that "toggled on" during the first pass gets "toggled off" again during the second, landing back at all-off, regardless of what the original pattern was.

The classic application: given an array where every number appears exactly twice except one number that appears once, find the lone number — in a single pass, XOR every element together.

🧠 WHY XOR-ING THE WHOLE ARRAY TOGETHER LEAVES ONLY THE LONE SURVIVOR

XOR is both commutative and associative — the order you XOR things together doesn't matter, only which values are included. So mentally regroup the whole array as pairs of matching duplicates, plus the one lone survivor sitting off to the side. Every matching pair, XORed together, cancels perfectly to zero (Section 17.4's core fact) — and XOR-ing a bunch of zeros together, plus the lone survivor, plus Section 17.4's "XOR with 0 changes nothing" rule, leaves exactly the lone survivor and nothing else. The entire array collapses to a single answer in one O(n) pass, using O(1) extra space — no hash map needed to count occurrences, a genuinely meaningful upgrade over the more obvious hash-map-based approach, purely by exploiting this self-cancellation property.

17.5Shifting as multiplying, made concrete

Why sliding the switches left or right is exactly multiplication or division by 2

+

n << k shifts every switch k positions to the left (filling the newly-opened low positions with off), and n >> k shifts every switch k positions right. Worth connecting this directly to ordinary base-10 intuition, rather than treating it as a separate rule: shifting every digit of a base-10 number one place to the left — 47 becoming 470 — is exactly multiplying by 10, because each digit's positional value grows by a factor of 10 when it moves one place over. Binary works identically, just with each position worth a power of 2 instead of a power of 10 — shifting every switch one place left doubles every switch's contribution, which is precisely multiplication by 2.

17.6A whole set living inside one integer

The payoff this entire chapter has been building toward

+

Here's where Section 17.1's light-switch picture pays off completely: if you have up to 32 (or 64) small, distinct items, you can represent an entire subset of them as a single integer — switch i being "on" means item i is currently in the set. This is exactly the mechanism Chapter 15.8 gestured toward for bitmask DP, finally made concrete.

🎛️ THE CONTROL-PANEL ANALOGY

Picture a control panel with one switch per item — item 3's switch on means "item 3 is currently in my selected set." Checking whether item 3 is in the set is just glancing at switch 3. Adding item 3 to the set is flipping switch 3 on. Removing it is flipping switch 3 off. Every one of these operations touches exactly one switch, instantly, without needing to inspect or rebuild anything else on the panel — a dramatic contrast to, say, checking membership in a plain list, which might need to scan every entry.

🧠 WHY THIS IS EXACTLY WHAT MADE BITMASK DP PRACTICAL

Recall Chapter 15.8's bitmask DP state — dp[mask][i], representing "having visited exactly this set of cities." Without this chapter's tools, "exactly this set" would need to be represented some other way — perhaps a Python tuple or frozenset used as a dictionary key — genuinely workable, but slower, since comparing and hashing a general set-like structure costs more than comparing two plain integers. Representing the visited-set as a single integer bitmask means every state comparison, every "have I visited this exact combination before" check, is as fast as comparing two ordinary numbers — which is precisely why bitmask DP's O(2ⁿ · n²)-shaped state space, while still exponential, remains genuinely practical for the range of n it's typically used for (roughly up to 20), rather than being needlessly slowed down further by clunky set representations on top of an already-large state space.

17.7Where smart people trip up

Explained through why the confusion happens

+
⚠️ MISTAKE 1 — Forgetting the n > 0 guard on the power-of-2 check

Section 17.2's n & (n-1) == 0 test relies on n having exactly one on-switch — but n = 0 has zero on-switches, and the domino trick applied to 0 still produces 0, satisfying the same check despite 0 not being a power of 2 at all. Always explicitly guard with n > 0 alongside this check, or the test will silently misclassify zero.

⚠️ MISTAKE 2 — Assuming right-shift on negative numbers behaves like plain division

Section 17.5's "shift is division by 2" intuition is clean for non-negative numbers, but right-shifting a negative number in many languages performs an "arithmetic" shift that preserves the sign, which doesn't always match what plain integer division (which typically rounds toward zero) would give — the two can disagree on negative inputs. Worth explicitly testing shift behavior on negative numbers in whatever language you're using, rather than assuming the positive-number intuition transfers unchanged.

⚠️ MISTAKE 3 — Using XOR to find a lone survivor when the "everyone else appears twice" assumption doesn't actually hold

Section 17.4's trick specifically depends on every other value appearing an even number of times (any even count cancels via repeated pairing, not just exactly twice) — if the problem's actual guarantee is different (say, "everyone else appears three times," an odd count), naive XOR-ing the whole array won't isolate the right answer at all, since odd-count values don't fully cancel out. Always confirm the exact repetition guarantee a problem is making before reaching for this specific trick.

⚠️ MISTAKE 4 — Running out of bits for the bitmask when n is too large

Section 17.6's bitmask-as-set trick is bounded by how many bits a single integer comfortably holds (32 or 64, depending on context) — attempting to represent a set of, say, 40 items this way in a language or context with fixed-width integers risks silent overflow or truncation. This is exactly why bitmask DP is described as practical "up to roughly n=20" — well within any reasonable integer width, with comfortable room to spare, rather than pushing right up against a hard limit.

17.8Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Using the odometer-ripple picture, explain exactly why n & (n-1) clears only the lowest on-switch and nothing else.›

Subtracting 1 flips the lowest on-switch off and flips every switch below it on (since they were all off, being below the lowest "on" position) — an odometer-style ripple. Everything above the lowest on-switch is untouched by this ripple, staying identical in both n and n-1. ANDing the two together only keeps switches that were on in both: the lowest switch was on in n but off in n-1, so it's cleared; everything below was off in both, staying off; everything above matched in both, staying exactly as it was.

Q2 — Why does the XOR-based lone-survivor trick work with O(1) extra space, when the "obvious" approach (a hash map counting occurrences) needs O(n) space?›

The hash-map approach needs to remember every distinct value's count, which genuinely requires space proportional to the number of distinct values. XOR-ing everything together instead exploits a mathematical cancellation property directly — every matching pair XORs to zero, regardless of which specific value it was, so there's no need to remember or count anything at all. The running XOR total is just a single number, updated in place as you go, with no per-value bookkeeping required.

Q3 — Why is "shifting is multiplication by a power of 2" a genuine mathematical fact rather than just a coincidental shortcut?›

Each switch's position represents a specific power of 2, exactly like each digit's position in base-10 represents a specific power of 10. Moving every switch one place to the left is identical, structurally, to moving every base-10 digit one place to the left (which is multiplication by 10) — each switch's contribution to the total value doubles when it moves one position over, because the next position over is worth exactly twice as much. It's the same positional-value logic underlying ordinary place-value arithmetic, just with base 2 instead of base 10.

Q4 — Using the control-panel picture, explain why checking set membership via a bitmask is faster than checking membership in a plain list.›

Checking a specific switch's state on the control panel is a single, direct glance — no need to inspect any other switch. Checking membership in a plain list, by contrast, generally requires scanning entries one by one until a match is found or the list is exhausted, an O(n) cost in the worst case. The bitmask's structure lets you address exactly the bit you care about directly, the same "address math instead of walking" idea from Chapter 2's parking lot, applied here to set membership instead of array access.

Q5 — Why does bitmask DP's use of integers instead of general set structures matter for practical performance, not just theoretical complexity?›

The overall state space (2ⁿ possible subsets) is already exponential regardless of representation — that part doesn't change. But representing each state as a plain integer, rather than a general set-like structure, makes every individual comparison and hash lookup genuinely cheaper (comparing two integers is faster than comparing two general sets), which matters a great deal when that comparison is happening an enormous number of times across the whole exponential state space — the representation choice doesn't change the complexity class, but it meaningfully changes the real, practical constant factor.

Q6 — Why does n & (-n) isolate the same lowest bit that n & (n-1) clears, rather than some other bit?›

Two's complement negation (flip every switch, then add 1) causes the "add 1" ripple to flip the newly-off lowest-original-on-switch back on, while the flip step has already forced every other switch to disagree with n's original pattern everywhere else. This means -n agrees with n at exactly one position — the original lowest on-switch — and disagrees everywhere else, so ANDing n and -n together keeps only that one shared position, the exact same lowest on-switch that n & (n-1) was clearing, just isolated here instead of removed.

Every trick in this chapter collapses to the same picture: a number is a row of light switches, and bulk operations on that entire row happen in a single instruction. Once that picture is genuinely internalized, nothing here needs to be memorized as a separate incantation — it can all be re-derived on the spot.
