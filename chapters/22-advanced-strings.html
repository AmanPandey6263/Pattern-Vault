Advanced Strings

Chapter 3 solved "find one pattern in one text." This chapter solves the harder, more common real-world version: find many patterns at once, or answer arbitrary substring questions about one huge text — by combining Chapter 3's KMP failure function with Chapter 13's trie.

22.1Matching many patterns at once

Why running KMP once per pattern is genuinely the wrong approach at scale

+

Given a text and a dictionary of thousands of patterns (think: a spam filter checking a message against thousands of banned phrases simultaneously), running Chapter 3.5's KMP once per pattern costs O(text_length × number_of_patterns) — for thousands of patterns, that multiplies out to something genuinely too slow.

💡 THE INSIGHT: MANY PATTERNS SHARE PREFIXES, EXACTLY LIKE CHAPTER 13'S WORDS DID

Chapter 13 built a trie specifically because many words share prefixes and shouldn't be stored (or searched) redundantly. The exact same observation applies here — thousands of banned phrases very often share common beginnings. Aho-Corasick is the answer: combine all patterns into a single trie (Chapter 13's structure), then add Chapter 3.5's KMP failure-function idea directly on top of it, letting you scan the text once, checking against every pattern simultaneously, in O(text_length + total_pattern_length) — not multiplied together, added.

22.2Aho-Corasick — a trie with shortcuts

KMP's "don't forget what you already know" idea, generalized to a whole trie

+

Recall Chapter 3.5's KMP insight exactly: on a mismatch, don't restart from scratch — jump using information the pattern already told you about its own structure (the LPS array). Aho-Corasick asks the same question, but for an entire trie of patterns at once: "if I'm partway down this trie hallway and hit a dead end, is there some other hallway, representing a shorter suffix of what I've matched so far, that I can jump to instead of restarting from the root?"

🔗 THE "FAILURE LINK" AS A GENERALIZED KMP JUMP

Every node in the Aho-Corasick trie gets a failure link — a pointer to the node representing the longest proper suffix of the current path that is also a prefix present somewhere else in the trie (exactly the LPS array's definition, Chapter 3.5, just computed across an entire trie of patterns instead of one single pattern). When scanning the text and hitting a character with no matching child, follow the failure link instead of restarting at the root — you've just reused Chapter 13's shared-structure idea and Chapter 3.5's "don't forget what you matched" idea in the same data structure, simultaneously.

🧠 WHY THE TEXT POINTER STILL NEVER MOVES BACKWARD — THE SAME O(n) GUARANTEE AS CHAPTER 3.5

Exactly as in plain KMP, the pointer scanning through the text only ever advances forward — only the position within the trie jumps backward via failure links, and it does so using precomputed information rather than blind restart. This preserves the same clean linear guarantee: scanning the whole text costs O(text_length), and building the failure links across the whole trie costs O(total_pattern_length) — added together, not multiplied, which is the entire reason this beats running separate KMP passes per pattern.

22.3Suffix arrays — every suffix, sorted

A different generalization: many questions about ONE huge text

+

A different, equally common need: given one enormous text, answer many different substring questions against it (does this pattern appear, what's the longest repeated substring, how many distinct substrings exist) — a suffix array is a sorted list of every possible suffix of the text, represented as starting indices rather than copying the actual substrings (which would waste O(n²) space).

📚 THE "SORT EVERY POSSIBLE ENDING OF THE BOOK" PICTURE

Imagine every possible way of starting to read a book from some point onward and continuing to the end — "starting from page 1," "starting from page 2," and so on — as distinct "documents," and sorting all of these documents alphabetically. Once sorted, searching for whether a specific phrase appears anywhere in the book becomes Chapter 5's binary search over this sorted list of starting points — since any suffix beginning with your search phrase will be sorted next to other suffixes sharing that same beginning, exactly the same "shared prefixes cluster together" idea from Chapter 13's trie, just expressed through sorted order instead of a tree structure.

✅ WHY THIS IS WORTH KNOWING EXISTS, EVEN WITHOUT FULL IMPLEMENTATION DEPTH HERE

Building a suffix array naively (sort all n suffixes directly) costs O(n² log n) — genuinely too slow for large texts, since each of the n suffix comparisons can itself cost O(n). Efficient construction (O(n log n) using a clever repeated-doubling comparison scheme, or O(n) with more advanced techniques) is a real, deep topic in its own right, deliberately beyond this book's scope to fully derive — but recognizing "many questions about substrings of one huge, unchanging text" as the signal to reach for a suffix array (or a suffix automaton, a related structure) is itself a valuable, transferable piece of pattern-recognition, even if you'd look up or use a library implementation of the construction algorithm in practice.

22.4Where smart people trip up

+
⚠️ Reaching for Aho-Corasick when there's only one pattern

The whole payoff — amortizing the failure-link construction across many patterns — evaporates with a single pattern, where plain KMP is simpler and just as fast. Aho-Corasick earns its complexity specifically when the number of patterns is large enough that per-pattern KMP passes would genuinely add up.

⚠️ Forgetting that a node's failure link must itself be fully computed before dependent nodes can use it

Failure links are built level by level (a BFS-order construction, echoing Chapter 14.2's queue-based exploration) — building them in the wrong order means a node's failure link might point to another node whose own failure link hasn't been finalized yet, silently producing incorrect jumps.

⚠️ Assuming a suffix array is "always" the answer for string problems

Suffix arrays specifically shine for many queries against one fixed, unchanging text — exactly like Chapter 2.4's prefix-sum trade-off. For a single one-off substring search, or frequently-changing text, this heavy upfront construction is a poor trade, and simpler tools (or a trie, for prefix-specific needs) are the honest choice instead.

22.5Check your understanding

+
Q1 — Why is Aho-Corasick better described as "KMP plus a trie" rather than a wholly new idea?›

It reuses Chapter 13's trie to physically merge patterns that share prefixes, avoiding redundant storage and redundant matching work — and it reuses Chapter 3.5's exact "don't restart from scratch on a mismatch" failure-function idea, just generalized so the jump target can be any node in the shared trie rather than a position in a single pattern. Both of its core ideas were already fully derived in earlier chapters; this chapter just shows they combine.

Q2 — Why does a suffix array store starting indices rather than the actual suffix substrings themselves?›

Storing every suffix as an actual copied substring would need O(n²) total space (the suffixes get progressively shorter, but their total combined length is still quadratic in n) — storing just the starting index of each suffix costs O(n) space total, since comparisons can always be done by looking back at the original text using the stored index, without ever needing a separate physical copy of each suffix.

Nothing in this chapter was a new fundamental idea — Aho-Corasick is Chapter 3 and Chapter 13 meeting each other, and suffix arrays are Chapter 5's binary search meeting Chapter 3's substring reasoning. That's genuinely the pattern across this entire book's "advanced" material: depth comes from combination, not from an ever-growing pile of unrelated tricks.

  • Contest-specific tricks (sqrt decomposition, heavy-light decomposition, persistent structures) — genuinely advanced-competitive-programming territory, only worth it if you're specifically pushing into Codeforces-style contests rather than interview prep.
