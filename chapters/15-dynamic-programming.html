15.1The two requirements, revisited properly

Not every slow recursive function is fixable this way — here's how to tell

+

Chapter 1.5 showed naive Fibonacci recomputing the same sticky-note answers over and over, and fixed it by writing each answer down once. But that fix only worked because Fibonacci happened to have two specific properties — and it's worth being precise about both, because DP genuinely doesn't apply to every slow recursive function you'll meet.

Overlapping subproblems: the same smaller question gets asked multiple times across different branches of the recursion — fib(3) was needed by both fib(5)'s direct path and fib(4)'s subtree. If a recursive function never actually asks the same question twice, there's nothing to cache, and memoization buys you nothing at all.

Optimal substructure: the best answer to the big problem can genuinely be built out of the best answers to its smaller subproblems, with no need to reconsider decisions once made. This is the subtler of the two — it's not just "the problem breaks into smaller pieces," but specifically that solving those pieces optimally, independently, and then combining them, is guaranteed to give the overall optimal answer.

💡 A CASE WHERE OPTIMAL SUBSTRUCTURE GENUINELY FAILS, WORTH SEEING ONCE

Consider "find the longest simple path between two nodes in a graph" (a path visiting no node twice). It's tempting to think: find the longest path from A to some midpoint M, find the longest path from M to B, glue them together. But this can break — the two "optimal" sub-paths might both pass through some shared node, and gluing them together would revisit that node, violating the "simple path, no repeats" rule entirely. The locally optimal pieces don't combine into a globally valid answer here, which is exactly why this specific problem resists a clean DP formulation the way shortest-path problems don't — optimal substructure is a genuine, checkable property, not something to assume by default just because a problem has smaller sub-versions of itself.

Both properties need to hold before reaching for DP. If subproblems overlap but there's no meaningful "optimal" choice being made (just one deterministic answer, like Fibonacci itself), memoization still helps — you're just caching, not truly optimizing over choices. If there's a choice to optimize over but nothing overlaps, plain recursion or a greedy approach (Chapter 16) might already be enough, and adding a memo table would be pure overhead with no payoff.

15.2Top-down vs bottom-up — filling the same table two ways

Two genuinely different ways to arrive at the identical answer

+
📖 THE "READ THE STORY BACKWARD, OR TELL IT FORWARD" ANALOGY

Top-down (memoization): write the recursive function exactly the way you'd naturally think about the problem — "to solve the big case, I need these smaller cases" — and just add a cache. This is like starting at the end of a story and asking "how did we get here?", tracing backward through cause and effect, writing down each answer the first time you work it out so you never have to re-derive it. Bottom-up (tabulation): start from the smallest, simplest base cases and build forward, filling in a table in an order that guarantees every value you need has already been computed by the time you need it — telling the story forward from the very beginning, chronologically, instead of working backward from the ending.

# Top-down — looks exactly like Chapter 1.5's memoized fib
memo = {}
def fib(n):
    if n <= 1: return n
    if n in memo: return memo[n]
    memo[n] = fib(n-1) + fib(n-2)
    return memo[n]

# Bottom-up — same answers, built forward instead of backward
def fib(n):
    if n <= 1: return n
    dp = [0, 1]
    for i in range(2, n+1):
        dp.append(dp[i-1] + dp[i-2])
    return dp[n]

Both cost O(n) time and produce identical results — the difference is genuinely just direction of construction, not correctness or, usually, complexity class. Top-down tends to be easier to derive, since it mirrors the natural recursive thought process directly — write the recursion first, worry about caching second. Bottom-up tends to be easier to optimize for space, because building forward through a table often reveals that you only ever need the last one or two rows, letting you collapse the whole table down to a couple of rolling variables (exactly what the Fibonacci example above could still be shrunk further to, using only two variables instead of a full array).

🧠 WHY BOTTOM-UP CAN ALSO AVOID CHAPTER 8's RECURSION-STACK COST

Recall Chapter 8's warning: recursion secretly costs O(depth) stack space, even when no explicit data structure is being built. Top-down DP is still recursion underneath the caching, so it still pays this hidden cost — a deep enough recursion (say, n in the hundreds of thousands) can genuinely hit a stack-depth limit that bottom-up's plain iterative loop never risks at all. This is a real, practical reason to prefer bottom-up specifically when n could be large, beyond just "personal style."

15.3The actual process for deriving a DP solution

A repeatable checklist, not a trick you either see or don't

+

DP has an unfair reputation as something you either magically "see" or don't. In practice, it's a genuinely repeatable process — the same four questions, asked in order, every time.

✅ THE FOUR QUESTIONS, IN ORDER

1. Define the state, in plain words. Not "dp[i]" as a symbol — actually write out, in a sentence, exactly what dp[i] (or dp[i][j]) represents. "dp[i] = the maximum value achievable using only the first i items" is a real definition; "dp[i] = the answer" is not.

2. Find the recurrence, by asking "what's the last decision?" This is the single most transferable trick in this whole chapter: instead of trying to see the whole solution at once, ask what choice was made last — was the last item taken or skipped? Was the last character matched or not? Answering that one question honestly usually reveals exactly how dp[i] relates to smaller states.

3. Identify the base case(s). The smallest state(s) that can be answered directly, no delegation — exactly Chapter 7.2's base-case discipline, applied here.

4. Decide the fill order (if bottom-up), or trust the cache (if top-down). Make sure every state a given cell depends on has already been computed by the time you need it.

The rest of this chapter is really this same four-question process, applied to five classic problems — worth reading each one specifically watching for how the four questions get answered, not just memorizing the final recurrence.

15.40/1 Knapsack — the backpack that won't reuse an item

The "last decision" question, applied for the first time

+
🎒 THE PACKING-FOR-A-TRIP ANALOGY

You're packing a bag with a strict weight limit, choosing from a set of items each with its own weight and value, wanting to maximize total value without exceeding the limit — and crucially, each item exists in only one copy, so once packed, it can't be packed again. Standing at the very last item on your list, deciding whether to include it, you have exactly two options: leave it out entirely (your total value is whatever the best you could do with everything else and the full weight limit still available), or take it (your total value is this item's value, plus the best you could do with everything else and the weight limit reduced by this item's weight).

State: dp[i][w] = the maximum value achievable using only the first i items, with total weight capacity w. Recurrence (the "last decision" question, applied):

dp[i][w] = max(   dp[i-1][w], // leave item i out   dp[i-1][w - weight[i]] + value[i] // take item i (only valid if weight[i] ≤ w) )

Base case: dp[0][w] = 0 for all w — zero items considered means zero value, regardless of available capacity.

🧠 WHY ITERATING WEIGHT IN REVERSE MATTERS WHEN COLLAPSING TO 1D

The 2D table can be collapsed to a single 1D array (since dp[i][...] only ever depends on dp[i-1][...], the immediately previous row) — but this collapse has a genuine trap worth understanding, not just memorizing as a rule. If you update the 1D array by iterating weight from low to high, then by the time you compute dp[w] for a middling weight, dp[w - weight[i]] might have already been updated during this same pass for item i — meaning you'd accidentally be allowed to use item i twice within a single "row," turning 0/1 knapsack into unbounded knapsack (Chapter 6's counting-sort-style "reuse allowed" story) by mistake. Iterating weight from high to low instead guarantees every value you read during item i's update still reflects the state from before item i was considered at all — preserving the "each item used at most once" rule the problem actually requires.

15.5Longest Common Subsequence

Proving the recurrence, not just stating it

+

Given two strings, find the length of the longest subsequence (not necessarily contiguous, but order-preserving) common to both — "ABCBDAB" and "BDCABA" share the subsequence "BCBA," for instance.

State: dp[i][j] = the length of the longest common subsequence between the first i characters of string 1 and the first j characters of string 2. The last-decision question: look at the very last characters, s1[i-1] and s2[j-1] — do they match?

if s1[i-1] == s2[j-1]: dp[i][j] = dp[i-1][j-1] + 1 else: dp[i][j] = max(dp[i-1][j], dp[i][j-1])
🧠 WHY MATCHING CHARACTERS ARE ALWAYS SAFE TO INCLUDE — A GENUINE PROOF, NOT JUST A RULE

This deserves an actual justification, in the spirit Chapter 9 and 14 kept insisting on: if s1[i-1] equals s2[j-1], is it always correct to greedily include this matching pair in the LCS, rather than possibly skipping it in favor of some other arrangement? Here's the exchange argument: suppose some optimal LCS exists that does not use this specific matching pair. That LCS's own last characters (whatever they happen to be) still had to come from somewhere at or before position i-1 in s1 and j-1 in s2 — but since s1[i-1] and s2[j-1] match each other, you could always swap in this matching pair as the LCS's final character instead, without shortening the LCS at all (you're just substituting one final matching character for another). This means an LCS using this pair is always at least as good as any LCS that doesn't — so greedily taking a matching pair when you find one never costs you anything, which is exactly what licenses the clean dp[i-1][j-1] + 1 recurrence.

When they don't match, neither character can jointly contribute to this position of the LCS, so the best you can do is fall back to the better of "ignore this character of s1" or "ignore this character of s2" — trying both and taking the max, since there's no way to know in advance which one will turn out to matter less without just checking.

15.6Edit distance — three honest moves

A direct extension of LCS's thinking, with one more option on the table

+

The minimum number of single-character insertions, deletions, or substitutions needed to turn one string into another. This is genuinely LCS's sibling — same "look at the last characters" question, with one extra option available when they don't match.

if s1[i-1] == s2[j-1]: dp[i][j] = dp[i-1][j-1] // characters already match, no edit needed here else: dp[i][j] = 1 + min(   dp[i-1][j], // delete s1[i-1]   dp[i][j-1], // insert s2[j-1]   dp[i-1][j-1] // substitute s1[i-1] for s2[j-1] )
🧠 WHY EACH OF THE THREE OPTIONS MAPS TO A SPECIFIC MOVE ON THE STATE GRID

This is worth genuinely visualizing as movement through the dp table, not just an arithmetic rule. Moving from dp[i-1][j] to dp[i][j] means "I consumed one more character of s1 without consuming a new character of s2" — exactly what a deletion does. Moving from dp[i][j-1] to dp[i][j] means the opposite — consuming a new s2 character without consuming a new s1 character, exactly an insertion. Moving from dp[i-1][j-1] to dp[i][j] means consuming one character from both strings at once — exactly a substitution (or, in the matching-character case above, a free non-edit). Every arrow into a table cell corresponds to a specific, real edit operation, and the recurrence is just "try all the moves that could have led here, keep whichever was cheapest."

15.7LIS — from O(n²) down to O(n log n)

A genuinely clever optimization worth seeing built up, not dropped in whole

+

Longest Increasing Subsequence: given an array, find the length of the longest subsequence where each element is strictly bigger than the one before. The naive DP: dp[i] = length of the longest increasing subsequence ending exactly at index i, computed by checking every earlier index j and extending whichever valid one gives the longest result — an honest O(n²), the familiar triangle-loop shape from Chapter 1.4.

There's a genuinely different, faster approach worth building intuition for, not just accepting.

🃏 THE PATIENCE-SORTING CARD PILES ANALOGY

Imagine dealing cards one at a time, building a row of piles under one strict rule: a card can only be placed on top of a pile whose current top card is bigger than it; if no such pile exists, start a brand new pile to the right of all existing ones. Here's the insight worth sitting with: the number of piles you end up with is exactly the length of the longest increasing subsequence — because every time you're forced to start a new pile, that's genuine proof you've found a value that couldn't extend any existing increasing run, meaning the LIS truly did grow by one. And crucially, placing a card on the leftmost valid pile (the one with the smallest top card that's still bigger than your current card) is always the safest, most flexible choice — it keeps every pile's top card as small as possible, maximizing the chance that future cards will find somewhere to go rather than being forced to start yet another new pile unnecessarily.

Translated into code: maintain an array tails, where tails[k] is the smallest possible "top card" (ending value) among all increasing subsequences of length k+1 discovered so far. For each new number, use Chapter 5's binary search to find the leftmost pile it can legally sit on (the first tail that's ≥ the current number), and either replace that pile's top card or, if none qualifies, append a brand new pile.

tails = []
for num in nums:
    pos = bisect_left(tails, num)   # Chapter 5's binary search — find leftmost valid pile
    if pos == len(tails):
        tails.append(num)            # no valid pile — start a new one
    else:
        tails[pos] = num              # replace this pile's top card with a smaller one
# len(tails) is the LIS length
🧠 WHY BINARY SEARCH IS EVEN VALID HERE — THE PROPERTY THAT MAKES IT WORK

Binary search (Chapter 5) requires a monotonic, no-flickering structure to search over — and it's worth confirming tails genuinely has that property, rather than just trusting it does. Every update to tails either extends it by exactly one element (always bigger than the current last element, by definition of needing a new pile) or replaces an existing entry with something smaller than it was — and it's provable, by induction on the update rule itself, that tails stays sorted in increasing order after every single update. That sortedness is exactly the precondition Chapter 5 needs — without it, binary-searching for the right pile wouldn't be valid at all, and this whole optimization would collapse.

Worth being honest about one subtlety: tails itself, at the end, is generally not an actual valid increasing subsequence from the original array — it's a bookkeeping structure tracking the best possible tail values, and its final length is what's meaningful, not its literal contents.

15.8Interval DP and bitmask DP, briefly

Two more shapes worth recognizing, even without full derivation

+

Interval DP

For problems asking about the best way to combine or process a contiguous range — matrix chain multiplication (in what order should you multiply a chain of matrices to minimize total operations), or burst-balloons-style problems (what order should you pop balloons to maximize points) — the state is naturally dp[i][j] = the best answer for the range from i to j, and the last-decision question becomes "what's the last split point k inside this range?" — trying every possible k and combining dp[i][k] with dp[k][j]. This is genuinely the same shape as Chapter 14.8's Floyd-Warshall (trying every possible waypoint), just applied to combining ranges rather than routing through nodes — worth noticing the family resemblance rather than treating them as unrelated tricks.

Bitmask DP

For problems where "which specific subset of items has been used so far" matters more than "how many have been used" — the classic example is a small-scale Traveling Salesman Problem, where the state needs to capture exactly which cities have already been visited, not just a count. Chapter 17's bit manipulation becomes directly useful here: represent the visited set as an integer bitmask (bit i set means city i has been visited), giving a state like dp[mask][i] = the minimum cost to have visited exactly the set of cities in mask, currently standing at city i. This state space is exponential (O(2ⁿ · n) states) — but for small n (roughly up to 20), it's a dramatic, genuine improvement over brute-force O(n!) permutation checking, echoing Chapter 7.6's honest distinction between wasteful exponential blowup and an honestly-sized problem: here, the exponential state space really is unavoidable given the "which exact subset" nature of the question, but it's still enormously better than the alternative.

15.9Where smart people trip up

Explained through why the confusion happens

+
⚠️ MISTAKE 1 — Writing the recurrence before precisely defining the state

Section 15.3's process insists on defining the state in a full, plain-language sentence first, and it's worth taking seriously as a warning: jumping straight to "dp[i][j] = ..." without first pinning down exactly what dp[i][j] means is the single most common way DP solutions go subtly wrong — the recurrence ends up combining values that don't actually represent compatible things, because the underlying definition was never made precise enough to check against.

⚠️ MISTAKE 2 — Forgetting the reverse-iteration trap when space-optimizing 0/1 knapsack

Section 15.4's specific warning, worth repeating directly: collapsing the 2D knapsack table to 1D without iterating weight in reverse silently allows items to be reused within the same pass, turning 0/1 knapsack into unbounded knapsack by accident — a bug that produces a plausible-looking, merely-too-high answer rather than a crash, making it genuinely easy to miss without a targeted test case.

⚠️ MISTAKE 3 — Assuming optimal substructure without checking it, following Section 15.1's warning

DP's reputation as broadly applicable can tempt people into assuming any problem with "smaller sub-versions of itself" is automatically DP-friendly. Section 15.1's longest-simple-path counterexample is exactly the kind of trap worth remembering — always sanity-check that locally optimal sub-answers genuinely combine into a valid, globally optimal answer, rather than assuming it by default.

⚠️ MISTAKE 4 — Filling a bottom-up table in the wrong order

Bottom-up DP requires that every state a given cell depends on has already been computed before that cell is reached — for a 2D table, this often means a specific nested-loop order (rows before columns, or vice versa, depending on the recurrence's actual dependencies) isn't just a style choice, it's a correctness requirement. Filling in the wrong order means reading a cell that hasn't been properly computed yet, silently using a stale default value (often zero) instead of the real answer.

15.10Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Why does the longest-simple-path example fail to have optimal substructure, even though it clearly breaks into smaller sub-versions of itself?›

Breaking into smaller sub-versions isn't sufficient on its own — optimal substructure specifically requires that combining the optimal answers to those sub-versions produces a valid optimal answer to the whole. Here, the two independently-optimal sub-paths might both pass through the same shared node, and gluing them together would revisit that node, violating the "simple path" rule the original problem actually requires. The pieces are individually optimal but don't combine into a valid overall solution, which is exactly what optimal substructure demands and what's missing here.

Q2 — What's the genuine practical reason to prefer bottom-up over top-down beyond personal taste, for large n?›

Top-down is still recursion underneath the caching, so it still pays Chapter 8's hidden O(depth) call-stack cost — for large enough n, this can genuinely hit a stack-depth limit and crash. Bottom-up's plain iterative loop never opens that recursive "waiting chain" at all, so it avoids this risk entirely regardless of how large n gets, which is a real, checkable reason to prefer it beyond just stylistic preference.

Q3 — Using the exchange argument, explain why LCS can safely, greedily include a matching character pair without ever needing to consider skipping it.›

Suppose some optimal LCS didn't use this specific matching pair — its own final characters had to come from somewhere at or before this position in both strings, but since these two specific characters match each other, you could always swap them in as the LCS's new final character without shortening the sequence at all. This means an LCS using the matching pair is always at least as good as one that doesn't, so greedily taking the match whenever found never costs anything — it's always a safe, correct choice.

Q4 — In edit distance, why does moving from dp[i-1][j] to dp[i][j] specifically correspond to a deletion, not an insertion?›

Moving from dp[i-1][j] to dp[i][j] means one more character of s1 has been accounted for (i increased) while no new character of s2 has been consumed (j stayed the same) — consuming an extra character of s1 without matching it to anything new in s2 is exactly what happens when you delete that character from s1. The direction of movement on the grid directly encodes which string "used up" a character, which is what ties each grid movement to a specific, real edit operation.

Q5 — In the LIS patience-sorting trick, why is placing a card on the leftmost valid pile always the safest choice, rather than just any valid pile?›

Placing on the leftmost valid pile keeps that pile's top card as small as possible going forward, which maximizes the chance that future cards will find a legal pile to extend rather than being forced to start an unnecessary new one. Choosing a pile with a bigger top card than necessary would "waste" flexibility — a smaller top card can accept strictly more future values than a bigger one can, so always minimizing the top card at every step keeps the structure as accommodating as possible for whatever comes next.

Q6 — Why is it valid to use binary search inside the LIS optimization, given Chapter 5's requirement of a monotonic, no-flickering structure?›

The tails array is provably kept sorted in increasing order after every single update — each update either appends a strictly bigger value than everything before it, or replaces an existing entry with something strictly smaller, and it can be shown by induction on this exact update rule that sortedness is preserved throughout. Since Chapter 5's binary search only requires this sortedness (or more generally, a monotonic, non-flickering property) to be valid, and tails genuinely has it, searching it with binary search is legitimate, not just a lucky coincidence.

Every DP problem in this chapter reduces to the same four honest questions from Section 15.3 — what does this state mean, what was the last decision, what's the base case, what order do I need to fill things in. The "trick" was never seeing the whole solution at once; it was learning to ask those four questions patiently, every single time.
