Advanced Dynamic Programming

Chapter 15 built the four-question process — state, recurrence, base case, fill order. This chapter proves that process genuinely transfers to state shapes that don't look anything like a simple array or 2D grid: a tree's structure, a number's digits, and a probability distribution.

21.1Tree DP — combining, but on a tree's shape

Chapter 10's recursive template, with an actual optimization decision layered in

+

Chapter 10.3 already gave you the shape: trust the left and right subtrees, combine their results. Tree DP is exactly this, except now there's a genuine choice to optimize over at each node, not just a fixed combination rule.

🏢 THE "INVITE THE EMPLOYEE, OR THEIR BOSS, NEVER BOTH" PROBLEM

Classic example: a company's org chart is a tree, each employee has a "fun score," and you want to invite the maximum total fun score to a party — with the rule that an employee and their direct manager can never both be invited (awkward). At every node, there are genuinely two different questions worth tracking, not one: "the best total fun score in this subtree, if this person is invited" and "the best total, if this person is not invited." If invited, none of their direct children can be — so you're forced to use each child's "not invited" value. If not invited, each child is free to be whichever is better — invited or not — so you take the max of the two for each child.

def solve(node):
    if not node:
        return (0, 0)   # (best if invited, best if not invited)
    invited, not_invited = node.fun, 0
    for child in node.children:
        c_inv, c_not = solve(child)
        invited += c_not              # child MUST be excluded if node is invited
        not_invited += max(c_inv, c_not)  # child is free either way
    return (invited, not_invited)
🧠 WHY TRACKING TWO VALUES PER NODE, NOT ONE, IS THE ACTUAL NEW IDEA HERE

Chapter 10's height and diameter each needed only a single number per node because there was no competing constraint to track. Here, "invited" and "not invited" are genuinely different states that lead to different obligations for the children — collapsing them into a single "best score for this subtree" number would lose exactly the information needed to correctly enforce the no-two-adjacent rule higher up the tree. This "track more than one state per node, because a single number can't capture the constraint" idea is the actual generalizable lesson — it reappears constantly in tree DP variants (maximum independent set, minimum vertex cover, tree coloring problems).

21.2Digit DP — counting without listing

Chapter 7.6's "honest count of real output" lesson, solved without generating the output

+

A classic question: "how many numbers between 1 and N have digit sum divisible by 7?" For N in the billions, actually iterating every number is hopeless. Digit DP answers this by processing digit-by-digit, left to right, tracking just enough state to know if you're still "tied" with N's own digits or already strictly less.

🔒 THE "STILL SHADOWING THE LIMIT, OR ALREADY FREE" IDEA

Imagine building a number digit by digit, left to right, while a strict chaperone (the number N) watches over your shoulder. As long as every digit you've placed so far exactly matches N's digit in that position, you're "tight" — the chaperone is still restricting your very next digit to be no bigger than N's corresponding digit. The moment you place a digit strictly smaller than N's in that position, the chaperone relaxes completely — every remaining digit can now be anything from 0-9 freely, since your number is already guaranteed smaller than N regardless of what comes after. This "tight vs. free" flag, plus whatever running property you care about (digit sum so far, mod some value), is exactly the DP state.

# state: (position, digit_sum_so_far % 7, is_tight)
def solve(pos, sum_mod, tight):
    if pos == len(N_digits):
        return 1 if sum_mod == 0 else 0
    if (pos, sum_mod, tight) in memo:
        return memo[(pos, sum_mod, tight)]
    limit = N_digits[pos] if tight else 9
    total = 0
    for d in range(0, limit + 1):
        total += solve(pos+1, (sum_mod + d) % 7, tight and d == limit)
    memo[(pos, sum_mod, tight)] = total
    return total
🧠 WHY THIS ACTUALLY COUNTS, RATHER THAN LISTS, AND WHY THAT'S THE ENTIRE POINT

The state space here is genuinely tiny — (number of digit positions) × (7 possible remainders) × (2 tight/free states) — so memoization collapses what would be an O(N) brute-force enumeration into something proportional to the number of digits of N, roughly O(log N). This is Chapter 15.1's overlapping-subproblems requirement in a new outfit: many different actual numbers share the exact same (position, sum_mod, tight) state, and digit DP is precisely the recognition that you never need to enumerate the numbers themselves — only the shared, compressed state that determines everything relevant about the count going forward.

21.3Probability & Expected Value DP

The same four-question process, where the "state" answers "on average," not "at best"

+

Instead of asking "what's the best possible outcome," expected-value DP asks "what's the average outcome, weighted by how likely each possibility is" — the recurrence structure is nearly identical to Chapter 15's, but max() or min() gets replaced by a probability-weighted sum.

🎲 THE "WEIGHTED AVERAGE OF WHAT HAPPENS NEXT" PICTURE

Classic example: expected number of dice rolls to go from 0 to reach exactly N on a number line, where each roll advances you by 1 to 6 (uniformly at random). Define E[i] = expected additional rolls needed, starting from position i. From position i, the very next roll takes you to i+1 through i+6, each with probability 1/6 — so the expected additional rolls from here is 1 (for this roll) plus the average of the expected remaining rolls from each of those six possible landing spots: E[i] = 1 + (1/6) * (E[i+1] + E[i+2] + ... + E[i+6]). This is precisely Chapter 15.3's "last decision" question, except the "decision" isn't something you control — it's a random outcome, and you're averaging over every way it could go, weighted by how likely each way is.

🧠 WHY THIS STILL HAS OPTIMAL SUBSTRUCTURE, JUST A DIFFERENT KIND

The "optimal substructure" Chapter 15.1 demanded isn't about choosing the single best sub-answer here — it's that the expected value from position i genuinely only depends on the expected values of the positions reachable from it, correctly weighted by their probabilities, with no need to reconsider how you arrived at i. This is a real, checkable structural property, not just wishful thinking: the future is independent of the past once you know your current position (a property called the Markov property, if you ever encounter that term), which is exactly what licenses building E[i] purely from E[i+1..i+6] without needing to know the full history of rolls that got you to i.

21.4Where smart people trip up

+
⚠️ Forgetting the "tight" flag in digit DP, or forgetting to memoize only the free (non-tight) states

The tight state is genuinely tied to N's specific digits, so results computed while tight aren't reusable across different numbers being counted — but once free, the sub-results depend only on (position, other state), and are safely reusable/memoizable. Some implementations skip memoizing tight states as an optimization; forgetting this distinction (or memoizing tight states incorrectly, mixing them with free ones) is a common, subtle bug.

⚠️ Writing expected-value recurrences "forward" instead of "backward"

It's tempting to define E[i] as "expected rolls to reach i from the start," but the clean recurrence in Section 21.3 only works defining E[i] as "expected remaining rolls from i to the end" — because the next step's uncertainty is naturally expressed in terms of what's still ahead, not what's already happened. Getting this direction backward tangles the recurrence into circular dependencies that don't resolve cleanly.

⚠️ Collapsing tree DP's two-state tracking into one value prematurely

As Section 21.1 warned, the temptation to just track "best score for this subtree" as a single number loses exactly the information a parent node needs to correctly enforce its own constraint. Before writing a tree DP recurrence, explicitly ask whether a single merged number is actually enough, or whether the problem's constraint requires tracking multiple "flavors" of the same subtree's answer.

21.5Check your understanding

+
Q1 — Why does the "invite the employee" tree DP need to track two values per node instead of one?›

A single "best score" number can't tell a parent node whether using it would violate the no-two-adjacent rule — the parent specifically needs to know the child's best score conditioned on whether the child was invited or not, since that determines what the parent is allowed to do. Collapsing to one number loses exactly the information needed to enforce the constraint correctly one level up.

Q2 — In digit DP, why does the "tight" flag matter for correctness, not just efficiency?›

Without it, there'd be no way to know whether the current digit is still constrained by N's own digit at this position, or free to be anything 0-9 — get this wrong and you'd either allow numbers bigger than N (overcounting) or wrongly restrict numbers that should be allowed (undercounting). It's not an optimization detail, it's the mechanism that keeps the count correctly bounded to exactly [1, N].

Q3 — Why is E[i] defined as "expected remaining rolls from i" rather than "expected rolls to reach i from the start"?›

The recurrence needs to express "what happens next" in terms of the uncertain future, not the already-fixed past — E[i] defined as remaining rolls depends cleanly on E[i+1] through E[i+6], values for positions strictly closer to the goal, giving a clean base case at the goal itself. Defining it as rolls-from-start instead would require knowing future randomness to compute a "past" quantity, creating a circular, unresolvable dependency.

None of these three variants required a new fundamental idea — every one of them is Chapter 15's four-question process, just applied to a state shape (a tree, a digit position, a probability) that doesn't look like a simple array index at first glance.
