Stacks & Queues

Two of the simplest structures in this whole book, and also two of the most quietly powerful — because the "order you're allowed to remove things" turns out to be exactly the right lens for an entire family of problems that otherwise look like they need something much more complicated.

Finally gives the monotonic stack idea, teased since Chapter 1, its full treatment

9.1The cafeteria tray stack

What a stack actually enforces, and why that matters

+

A stack is one of the simplest ideas in this entire book to state, and one of the most surprisingly deep to actually use well. The picture is almost too obvious to need explaining: a stack of cafeteria trays. You can only ever take the tray currently on top, and you can only ever add a new tray to the top too. You physically cannot reach into the middle of the stack and pull out the fifth tray down without first removing everything above it.

Only the top tray (19) is reachable — push adds here, pop removes here. This is LIFO: Last In, First Out.

This "last in, first out" rule — LIFO — sounds like a limitation, and in one sense it genuinely is: you're giving up the ability to reach arbitrary elements. But the entire value of a stack comes from this exact limitation matching a specific, extremely common real-world pattern: the most recently opened, most recently started, most recently unresolved thing is exactly the thing that needs to be dealt with next.

💡 WHY THIS PATTERN SHOWS UP EVERYWHERE

Think about your own function calls (Chapter 7's leap of faith): when function A calls function B, which calls function C, the computer needs to remember "come back to B once C finishes" and "come back to A once B finishes" — and the natural order to resolve these is exactly LIFO: the most recently started, still-unfinished call is exactly the one that needs to finish next, before anything earlier can continue. This isn't a coincidence — it's precisely why the very memory mechanism used to implement function calls is itself literally called "the call stack," and it's why Chapter 8's "recursion secretly costs memory" story and this chapter's stack picture are, underneath, the exact same structure.

9.2The ticket-counter line

The opposite ordering rule, and where it belongs instead

+

A queue enforces the exact opposite ordering rule — first in, first out, FIFO — and the picture is just as familiar: a line at a ticket counter. The person who's been waiting longest gets served next; new arrivals join at the back, not the front. You can't cut in line, and you can't get served out of turn just because you happened to be standing in a more convenient spot.

🎟️ WHY FIFO MATCHES "FAIRNESS" AND "IN-ORDER PROCESSING"

The natural situations where a queue is the right structure are ones where fairness or strict arrival-order genuinely matters: task scheduling (the job that's been waiting longest should generally get processed first), and — very importantly for this book — exploring a graph or tree level by level, where you want to fully finish visiting everything at the current "distance" before moving on to anything farther away. That level-by-level property is exactly what makes a queue the engine behind breadth-first search, which Chapter 14 covers in depth — the queue's FIFO discipline is precisely what guarantees you explore closer things before farther things.

Worth explicitly contrasting against Section 9.1: a stack is the right tool when "most recent, unresolved" should go next; a queue is the right tool when "longest waiting, oldest unresolved" should go next. Same basic idea — a container with restricted access — with the ordering rule flipped, and that single flip is what determines which real-world situations each one naturally models.

9.3Why nesting specifically needs a stack

A worked example that shows the LIFO rule isn't arbitrary here

+

The classic "valid parentheses" problem — checking whether a string like "({[]})" has every bracket properly opened and closed in the right order — is worth walking through slowly, because it's the clearest possible illustration of why LIFO specifically, and not just "some container," is the right fit.

🪆 THE NESTED-DOLLS-OF-BRACKETS ANALOGY

Picture nested brackets as nested boxes, one inside another. The very last box you opened has to be the very next one you close — you cannot close an outer box while an inner box is still sitting open inside it; that would leave the inner box permanently sealed inside a closed outer one, with no way to ever get back to it. This is exactly LIFO: the most recently opened bracket is mandatorily the next one that must close, before any earlier-opened bracket can close.

The algorithm becomes almost embarrassingly direct once you see this: push every opening bracket onto a stack as you encounter it. On every closing bracket, check whether it matches the bracket currently on top of the stack — if it does, pop it (that pair is resolved); if it doesn't, the string is invalid.

stack = []
pairs = {')': '(', ']': '[', '}': '{'}
for ch in s:
    if ch in "([{":
        stack.append(ch)
    else:
        if not stack or stack.pop() != pairs[ch]:
            return False
return not stack   # nothing left un-closed
🧠 WHY A QUEUE WOULD GENUINELY BREAK THIS

Worth actually trying to imagine the FIFO version, to feel why it's wrong, not just accept that it is: if you used a queue instead of a stack — checking the closing bracket against the oldest still-open bracket rather than the most recent one — then "({[]})" would incorrectly try to match its first ] against the outermost (, which is nonsense; the innermost, most-recently-opened bracket is exactly the one that logically must close first, and only LIFO access naturally enforces that. The data structure isn't an arbitrary implementation choice here — it's a direct, necessary match to the actual logical structure (nesting) of the problem being solved.

9.4The monotonic stack, built from scratch

The trick teased since Chapter 1, finally earned properly

+

Here's a genuinely common problem: given a row of buildings with different heights, for every building, find the next building to its right that's taller. The brute-force approach checks, for every building, every building after it — the familiar O(n²) triangle shape. There's a way to do this in a single O(n) pass, and it's worth building up slowly rather than just handing you the trick.

🏙️ THE SKYLINE-WATCHER ANALOGY

Imagine walking down a street of buildings, left to right, keeping a running list of every building you've passed whose "next taller building" question is still unanswered. Here's the key realization: this running list is always, automatically, sorted from tallest (at the bottom, oldest) to shortest (at the top, most recent) — because the moment you encounter a building tall enough to answer an earlier, shorter building's question, that shorter building gets resolved and removed from the list entirely; only buildings that are still taller than everything encountered so far after them remain on the list. This self-maintaining "shortest at the top" order is exactly what "monotonic stack" means — a stack that's kept, by construction, always increasing or always decreasing, never both.

stack = []   # holds indices, buildings we haven't resolved yet
answer = [-1] * len(heights)
for i, h in enumerate(heights):
    while stack and heights[stack[-1]] < h:
        resolved_index = stack.pop()
        answer[resolved_index] = i    # building i is its next-taller answer
    stack.append(i)

Trace this on [2, 1, 5, 3, 4] by hand: building 0 (height 2) pushes → stack: [0]. Building 1 (height 1, shorter) can't resolve anything → stack: [0, 1]. Building 2 (height 5) is taller than both buildings on the stack — it resolves building 1 first (answer[1]=2), then resolves building 0 too (answer[0]=2) — then pushes itself → stack: [2]. Building 3 (height 3, shorter than 5) can't resolve anything → stack: [2, 3]. Building 4 (height 4) resolves building 3 (answer[3]=4), but not building 2 (5 > 4, still taller) → stack: [2, 4].

🧠 WHY THIS IS GENUINELY O(n), PROVEN THE SAME WAY AS CHAPTER 4

This has the exact same "while loop inside a for loop" shape that Chapter 4.7 taught you to be suspicious of — and the same resolution applies. Every single building gets pushed onto the stack exactly once, ever, across the entire run. And every building gets popped at most once, ever — once resolved and removed, it never returns to the stack. So the total number of pushes and pops, summed across the entire algorithm, is bounded by 2n, not n² — the inner while loop's total work across the whole run is capped by how many things could ever be popped in total, which is n, exactly the same amortized argument from Chapter 4's sliding window and Chapter 2's cyclic sort. Same proof, new costume.

This exact pattern — "find the next/previous greater/smaller element" — is one of the highest-value patterns in this entire book to have genuinely internalized, because it quietly powers a surprising number of famous problems once you can recognize the shape: largest rectangle in a histogram, daily temperatures, trapping rain water (one common approach), stock span problems — all of them are this same skyline-watcher idea, wearing a different outfit.

9.5The min-stack — remembering without recomputing

A small, clean example of Chapter 2's prefix-sum idea, wearing a stack's clothes

+

Design a stack that supports the usual push and pop, but also an O(1) getMin() — instantly telling you the smallest element currently in the stack, at any moment, no matter how many pushes and pops have happened. The naive approach — scanning the whole stack every time getMin() is called — is O(n) per call, and the challenge is getting that down to O(1).

📋 THE "CARRY THE RUNNING RECORD ALONG WITH YOU" ANALOGY

This is genuinely the exact same idea as Chapter 2's prefix sums, just reshaped: instead of recomputing the minimum from scratch every time someone asks, carry along, at every single position in the stack, the answer to "what was the minimum of everything up to and including this point?" — precomputed once, as you go, rather than recomputed on demand.

Concretely: maintain a second, parallel stack that tracks the running minimum. Every time you push a value onto the main stack, also push the smaller of (this new value, the current running minimum) onto the min-stack. Every time you pop from the main stack, also pop from the min-stack.

main_stack = []
min_stack = []

def push(val):
    main_stack.append(val)
    current_min = min(val, min_stack[-1]) if min_stack else val
    min_stack.append(current_min)

def pop():
    main_stack.pop()
    min_stack.pop()

def get_min():
    return min_stack[-1]   # O(1) — already computed
🧠 WHY POPPING FROM MIN-STACK IN LOCKSTEP IS SAFE

Here's the detail worth actually justifying: when you pop the main stack's top value, is it safe to just blindly pop the min-stack too, without recomputing anything? Yes — because the min-stack's top entry, by construction, was specifically the minimum considering everything up to and including the value you're about to remove. Once that value is gone, the minimum you actually care about going forward is exactly what the min-stack's previous entry already recorded — the minimum up to the point just before the removed value was ever pushed. Nothing needs recomputing because the min-stack was built to already contain the correct answer for every possible "current state" of the main stack, one entry per push, precomputed and carried forward rather than derived on demand.

The cost of this O(1) getMin() is genuinely honest, not free: O(n) extra space for the parallel min-stack. Exactly Chapter 2's prefix-sum trade-off again — pay with memory, upfront and incrementally, to buy instant answers later, worthwhile specifically because getMin() is expected to be called often.

9.6Building one structure from its opposite

A genuinely fun exercise in really understanding what each structure guarantees

+

A classic exercise: implement a queue using only two stacks (or a stack using only two queues). This sounds like a strange party trick, but it's actually a great test of whether you genuinely understand LIFO and FIFO, or just their names.

🔄 THE "FLIP THE PILE OVER" ANALOGY

Imagine a pile of plates (a stack) that you want to serve people from in FIFO order instead. Here's the trick: if you take the entire pile and flip it upside-down onto a second, empty pile — plate by plate — the plate that used to be at the very bottom of the original pile (the oldest one, the first one ever added) ends up at the very top of the new pile. A stack's "top" is instantly accessible — so the oldest plate, exactly the one FIFO wants served next, is now sitting right where a stack naturally hands things over.

in_stack = []    # receives new elements
out_stack = []   # serves elements out, in FIFO order

def enqueue(val):
    in_stack.append(val)

def dequeue():
    if not out_stack:
        while in_stack:
            out_stack.append(in_stack.pop())   # flip the whole pile over
    return out_stack.pop()
🧠 WHY THIS IS STILL AMORTIZED O(1) PER OPERATION, NOT O(n)

The "flip the whole pile" step looks expensive — O(n) in the worst case — but notice it only happens when out_stack is completely empty, and crucially, once an element has been flipped into out_stack, it never gets flipped back; it just gets popped off directly on future calls until out_stack empties again. Using the exact same amortized-cost reasoning from Chapter 1.7 and Chapter 4.7: each individual element gets moved from in_stack to out_stack at most once, ever, across its entire lifetime in the structure. Summed over n total operations, the total flipping work across the whole run is bounded by n, giving O(1) amortized cost per operation — genuinely cheap on average, even though any single dequeue() call can occasionally trigger a burst of work.

9.7The deque and sliding window maximum

Combining this chapter with Chapter 4, for a genuinely elegant payoff

+

A deque (double-ended queue) allows O(1) push and pop from both ends — neither purely LIFO nor purely FIFO, but flexible at both ends. Its most elegant application: finding the maximum of every fixed-size sliding window (Chapter 4.4's caterpillar) in O(n) total, rather than the naive O(n·k) of recomputing the max for every window position from scratch.

🚶 THE "DON'T BOTHER TALKING TO THE SHORT GUY" ANALOGY

Picture a group of people walking in single file, and you want to know, as the group moves, who the tallest person currently within a moving "window" is. Maintain a list of candidates for tallest, kept in decreasing height order from front to back. Here's the trick: whenever a new person joins the back of the window, if they're taller than the person currently at the back of your candidate list, that shorter candidate can never possibly be the answer again — the new, taller person will outlast them in the window and is standing behind them (arrived later), so the shorter one is now permanently irrelevant. Kick them out of your candidate list entirely, and keep checking backward until you hit someone taller (or the list empties). This keeps your candidate list always sorted tallest-to-shortest, front-to-back — and the tallest person in the current window is always sitting right at the front.

dq = deque()   # stores indices, front-to-back = tallest-to-shortest
result = []
for i, val in enumerate(nums):
    while dq and nums[dq[-1]] < val:
        dq.pop()                 # the short guy can never win again — evict
    dq.append(i)
    if dq[0] <= i - k:
        dq.popleft()              # evict anyone who's aged out of the window
    if i >= k - 1:
        result.append(nums[dq[0]]) # front of the deque = current window's max
🧠 THIS IS THE MONOTONIC STACK AGAIN, WITH ONE EXTRA RULE

Notice this is genuinely the same skyline-watcher idea from Section 9.4 — evict everything that can never be the answer again — with one addition: elements can now also leave from the front, specifically because they've aged out of the sliding window, a concern the plain monotonic stack never had since it never needed to "forget" anything based on position. The complexity proof is identical in spirit too: every index gets pushed onto the deque exactly once and evicted (from either end) at most once, so total work across the whole run is bounded by 2n — genuinely O(n) for the entire sliding-window-maximum problem, not O(n) per window.

9.8Where smart people trip up

Explained through why the confusion happens

+
⚠️ MISTAKE 1 — Reaching for a stack or queue without asking which ordering the problem actually needs

Section 9.3 showed nesting problems genuinely need LIFO, and Section 9.2 showed level-by-level or fairness-based problems genuinely need FIFO — but under time pressure, it's easy to grab whichever structure comes to mind first rather than asking "does this problem's logic actually require most-recent-first, or oldest-first?" Getting this backward doesn't crash — it silently produces wrong output, which is a much harder class of bug to catch than an error message.

⚠️ MISTAKE 2 — Popping the min-stack conditionally instead of in lockstep

A tempting-looking but wrong "optimization" of the min-stack: only pop the min-stack when the popped main-stack value equals the current minimum, to "save space." This breaks the structure — if a duplicate value that happens to equal the current min gets pushed and later a different, earlier-pushed instance of that same value gets popped from below it, the bookkeeping gets confused about which "layer" of minimum is currently accurate. Always push and pop both stacks together, in strict lockstep, exactly as shown in Section 9.5 — the parallel structure only stays correct if it moves in perfect sync with the main stack, with no exceptions.

⚠️ MISTAKE 3 — Forgetting the deque needs eviction from BOTH ends

Section 9.7's sliding-window-maximum deque needs two genuinely separate eviction checks — one for "this element can never be the max again" (evicting from the back, based on value) and one for "this element has aged out of the window" (evicting from the front, based on position). Implementing only one of these two checks produces code that runs without error but silently gives wrong answers, since a stale, out-of-window index left sitting at the front would incorrectly be reported as the current window's maximum.

⚠️ MISTAKE 4 — Assuming a monotonic stack always stores values, never indices

Many monotonic stack problems (like Section 9.4's "next taller building") need to report a position (which building, not just what height), which means the stack needs to store indices, not the raw values themselves — you can always look up heights[stack[-1]] when you need the value for comparison. Storing raw values when the answer actually needs positions is an easy, avoidable mismatch that forces awkward workarounds later in the same solution.

9.9Check your understanding

Explain each one out loud, in your own words, before revealing the answer

+
6 questions explain in your own words first
Q1 — Using the nested-boxes picture, explain why a queue (FIFO) would genuinely break the valid-parentheses check, not just be "a different but equally valid" approach.›

A queue would match closing brackets against the oldest still-open bracket rather than the most recently opened one — but nesting logically requires the innermost, most-recently-opened bracket to close first, since it's physically "inside" everything opened before it. Matching against the oldest open bracket instead would try to close an outer box while an inner one is still open, which doesn't correspond to any valid nesting at all — it's not a stylistic difference, the FIFO version answers a different, wrong question.

Q2 — In the monotonic stack for "next taller building," why does a building only ever get pushed once and popped at most once?›

Each building is pushed exactly once, when it's first encountered walking left to right. Once it gets popped — meaning a later, taller building has resolved its "next taller" answer — it's permanently removed and never re-enters the stack, since there's no mechanism that ever pushes an already-resolved building back on. With n buildings each contributing at most one push and one pop across the whole run, total stack operations are bounded by 2n, which is exactly why the algorithm is O(n) despite the nested while-loop-in-a-for-loop shape.

Q3 — Why is it safe for the min-stack to just pop in lockstep with the main stack, without recomputing the minimum?›

Because every entry in the min-stack was built, at push time, to already record the correct minimum considering everything up to and including that specific position. Once the top value is popped from both stacks together, the min-stack's new top is exactly the minimum that was correct for the state just before the removed value was ever pushed — which is precisely the state you're returning to. Nothing needs recomputing because the correct answer for every possible "past state" was already precomputed and stored in parallel, one entry per push.

Q4 — In the two-stacks-make-a-queue trick, why is the amortized cost O(1) per operation despite the occasional full "flip"?›

Every individual element gets flipped from in_stack to out_stack at most once during its entire lifetime in the structure — once flipped, it just gets popped directly on future calls without ever being flipped again. So even though a single dequeue() call can occasionally trigger an expensive full flip, the total flipping work summed across all n operations in a long run is bounded by n, not n², giving O(1) amortized cost per operation — the same "expensive but rare, cancels out" reasoning as Chapter 1.7's dynamic array doubling.

Q5 — In the sliding window maximum, why does an evicted-from-the-back element get permanently discarded rather than possibly needed again later?›

An element gets evicted from the back specifically when a taller element arrives after it — and since that taller element will remain in every future window that still contains the shorter one (it arrived later, so it "outlasts" the shorter one within any shared window), the shorter element can genuinely never become the maximum of any future window as long as the taller one is still present. It's not a heuristic guess — it's a provable fact that the shorter element is permanently dominated from that point forward.

Q6 — What's the actual difference between why a stack is used in Section 9.3 (parentheses) versus Section 9.4 (next taller element) — are they using the LIFO property for the same reason?›

Not quite the same reason, though both lean on LIFO. Section 9.3 uses LIFO because the problem's own logical structure (nesting) genuinely requires "most recently opened, first closed." Section 9.4 uses a stack more as a bookkeeping device — maintaining a self-sorted list of "still-unresolved candidates" — where LIFO happens to be the right access pattern because newly arriving information (a taller building) always resolves the most recently added, still-pending candidates first, before potentially reaching further back. Both are genuinely LIFO, but one comes from the problem's inherent nesting structure, the other from how new information happens to resolve pending questions in reverse-recency order.

A stack and a queue are the same idea — a container with restricted access — with one property flipped. That single flip determines an enormous amount: which real-world problems each one models honestly, and which famous O(n) tricks (monotonic stacks, sliding window maximum) become available once you're willing to give up random access on purpose.
